## 摘要：这座平台真正的差异点

大多数比赛项目的技术含量集中在「调通了某个大模型」，本项目的技术含量集中在**四件更难的事**：

1. **让 LLM 输出可审计** —— 数字不许模型算，只许 SQL 算，外层再逐项对数（数字红线，双闸门）。
2. **让低代码编排与硬约束同时成立** —— 画布可以随便改拓扑，但护栏节点删不掉、非法的图发布不了。
3. **让 AI 能碰真实业务库而不出事** —— SQL 守卫 + 审计 + 人工审批重放，三道闸门。
4. **让「改了没生效」「200 但是假的」这类事故不再复发** —— 冒烟脚本能识别假 200，构建有产物校验门禁。

这四条都不是"加个框架"，是踩了坑之后固化成机制的，代码里留着事故复盘注释。

## 一、Top 6 主推（答辩就讲这六条）

### ① 数字红线：LLM 不许算数，算完还要对数

**卖点**：把"别编数字"从提示词口号变成可执行、可回归的机制，并且**区分了能判定的和不能判定的**。

**实现分三层：**

- **算法层（确定性计算）**：库存量、库龄分布、趋势全部走 SQL 聚合，Java 侧明确声明"不含任何自然语言生成"——  
  `aismp-agent/.../terminal/service/TerminalService.java:19`、`terminal/task/StockAlertScanner.java:26`
- **校验层（代码 diff，不走 LLM）**：`agent-orchestrator/graph.py:1102` `verify_numbers()`  
  逐项核对卡片里每个数字是否能在算法输出里找到**同值**来源；不一致就带上 `verify_violations` 回炉。
- **发布层（护栏删不掉）**：`agent-orchestrator/canvas/loader.py:58`  
  图画布上如果缺 `verify_numbers`，或者 `report` 直连 `respond` 绕过校验，**publish 直接 422**。

**最有说服力的一段是校验器自己的事故复盘**（`graph.py:1104-1114` 注释）：  
原实现用 `{model: qty}` 建期望表，同一个 model 被拆成多行时后写覆盖前写 → 期望合计算成 150，卡片如实汇总 171 → 每轮误判、白跑两次 report LLM（约 20s）→ 最后靠 `MAX_REVISIONS` 降级放行。  
改成按 key 累加后 **数字红线首次通过，report 调用 3→1 次，耗时 37.6s→30.8s**。

> 讲法：这不是"模型算错了"，是"**校验口径与算法输出不匹配**"。能定位到这一层，说明校验器是被当成生产组件在维护的。

**现场可验证**：管理台画布删掉 `verify_numbers` → 点发布 → 弹出红线违规错误列表。

### ② 画布 DSL → LangGraph：能编排，但护栏写死在编译期

**卖点**：低代码编排最常见的两个坑是"可视化 = 动态生成代码"和"改了图不知道线上跑的是哪版"，这两个都用结构化解掉了。

- **装配器只有两个循环，无递归、无 eval/exec**：`canvas/loader.py:21` 校验器 + `:79` `build_graph_from_dsl()`  
  `for n in nodes: add_node` / `for e in edges: add_edge` / `for c in conditional: add_conditional_edges`。
- **环不是特殊语法**：条件边回指上游天然成环（`on_rework → report`），收敛靠两道闸 —— `MAX_REVISIONS=2`（`graph.py:88`）+ 运行期 `recursion_limit=20`（`server.py:252`）。
- **能力与流程解耦**：`canvas/registry.py:168` `resolve_node()`，DSL 里只写 `type`，实现全在注册表；`graph.py` 一行未改就能被复用。自定义节点**只允许 http 形态**（`store.py:274`，注释明写"防 SSRF / 不允许自定义任意执行语义"）。
- **拓扑等价性回归测试**：同一份 `DEFAULT_DSL` 重建出的图，必须与手写 `build_graph()` 逐节点逐边完全一致（`tests/test_canvas_loader.py:29`）—— 防"两套拓扑事实来源漂移"，这是把重构安全性做成了自动断言。

**版本语义**：draft/published 双态 + 回滚 = "把旧 DSL 重新发布为新版本"（`store.py:224`，版本链不破坏）；  
草稿位唯一性用 PG 部分索引 `WHERE status='draft'` 保证（`store.py:27-29`），省掉应用层锁。

**现场可验证**：`deploy/server-docker/canvas_link_test2.py` —— 把 `entry` 改指 `chart_plan`，**执行路径必然改变**（判据来自 SSE 里真实的节点序列，不是模型自述），9/9 通过。

### ③ 网关三通道鉴权 + 身份注入作为数据权限信任根

**卖点**：同一入口同时承载三种凭证模型，并且明确回答了"浏览器不可能持有 AK/SK"这个真实约束；更关键的是把"客户端自报身份"彻底降级为不可信。

- **三通道分流**：`aismp-gateway/.../CustomGlobalFilter.java:144-170`  
  REST → AK/SK 签名；MCP（`/sse`,`/mcp/**`）→ Bearer（MCP 客户端只会带标准头）；门户 → Bearer。  
  `/api/terminal/**`、`/api/transferOrder/**` 是**双通道**：带 Bearer 走门户，无 Bearer 落 AK/SK（编排层作为服务方调）。
- **防重放三件套**：`sign = sha256(body + "." + sk)` + nonce `SETNX` + 5 分钟时间窗（`:262-281`）。  
  nonce 的 key 带 `accessKey` 前缀 —— 否则不同用户的巧合撞车会被误判成重放；  
  原 `>100000` 的校验被移除，注释算了碰撞概率（9 万空间、5 分钟 100 次，撞车 5%+）。
- **身份注入 = 信任根**（`:560-590`）：**先剥离**客户端自带的 `X-User-*`，**再注入**网关核验过的身份。  
  顺序不可反，注释里留着一次真实复现的洞：`/orchestrator/**` 原在 AK/SK 通道放行 → 第三方伪造 `X-User-Id` 即可冒充任意门户用户（已实测复现，已收口为门户专用）。
- **一个很能打的 SRE 细节**：整个 filter 被挪到 `Schedulers.boundedElastic()`（`:52-57, 121`），  
  因为 Gateway 跑在 `reactor-http-nio-*` 事件循环上，里面做阻塞 RestTemplate 会**整站失去响应**而不是单请求变慢；配套的 `RestTemplate` 显式设 2s/3s 超时（`config/LoadBalancedClientConfig.java:33`，"默认 -1 会耗尽弹性线程池"）。

### ④ AI 碰真实业务库的三道闸门（工具沙箱）

**卖点**：这条比任何 RAG 都更能证明"AI 工程"而非"调 API"。

1. **SQL 守卫** `digital-human/.../tool/SqlGuard.java:55`  
   只允许 `SELECT/WITH/SHOW/DESC/EXPLAIN`；中间出现分号即拒（末尾分号容忍）；危险关键字用**词边界正则**判定 —— 专门避免 `create_time` 被 `CREATE` 误伤。

**加分项**：`SqlGuardTest` 是自写的安全回归，16 个用例专门测"词边界不误伤""末尾分号""行数兜底"（`SqlGuardTest.java:108-197`）。

### ⑤ 调拨状态机：无版本字段也能挡住并发

**卖点**：状态机不是 if-else 堆的，是"单据状态校验 + 串码四重比对 + 在库存行上做 CAS + 影响行数断言"。

- 状态图写在注释里：`TransferOrderServiceImpl.java:60-66`  
  `APPLIED --B仓管出库--> OUTBOUND --A仓管入库--> DONE`，两侧各自可驳回 → `REJECTED`（在途退回调出仓可用）。
- **四重校验 + 数量严格相等**（`:296-335`）：串码存在 / 在调出仓 / 状态允许 / 型号在明细内；每个物料出库数量必须等于单据数量。
- **行级 CAS + 断言**（`:340-355`）：  
  `UPDATE terminal SET status=IN_TRANSIT WHERE status=#{原状态} AND serialNo IN (...)`  
  然后 `if (updated != distinct.size()) throw` → 事务回滚。比对与更新之间被别人改了，直接整单失败，不会出现"一半出库"。
- **性能顺带修掉一个 O(N) 往返**：`:292` 注释写明"逐条 selectById 是 N 次查询，一次调拨 2939 台就是 2939 次往返，是出库超时的元凶"，改成 `IN` 一次查完 + 按源状态分组批量更新。

### ⑥ 一次 301.8 秒的线上事故，变成了架构决策

**卖点**：最能体现"工程判断"而不是"堆技术"的案例。

原实现：图表选型走 LLM 优先 + `except: pass` 静默重试 3 次。提供方一抖动，整条链路拖到 **301.8 秒**，且日志零痕迹（`graph.py:271-276` 留着事故时间戳 17:15:45、293 秒）。

修复不是加重试，而是承认 **"5 选 1 的分类本质是规则活"**：

- 规则优先，命中 <1ms 完全不烧 LLM（`:582-592`）；顺序按具体度排列（`time` 最具体放最前）。
- 失败**必须留痕**再降级（`:610` `log.warning(...raw=%r)`），不许静默。
- **产品级取舍**：LLM 只定"初始样式"，同一份 `labels/series` 前端即时换图型，不重跑请求。

## 五、讲法建议

### 3 分钟版（只讲一条主线）

> "LLM 在我们系统里**不许算数**。库存、库龄、趋势全部 SQL 聚合出确定值，模型只负责组织语言；  
> 它组织完之后，还有一道代码级的对数闸门逐个核对每个数字，不一致就打回重写 —— 而且这道闸门**在画布上删不掉**，删了图发布不了。  
> 这套机制上线后我们发现，第一次失败不是因为模型算错，是**校验口径和算法输出不一致**（同一个型号被拆成三行），改完之后重试从 3 次降到 1 次、耗时降了 7 秒。"

### 10 分钟版（推荐顺序）

1. **痛点**：联通固网终端补货靠人工经验，跨仓调拨走线下 → 要"一句话出方案 + 闭环到建单"。
2. **数字红线**（①）—— 建立"可审计的 AI"这个基调。
3. **画布 DSL**（②）—— 说明平台化：流程可被业务方改，护栏改不掉。
4. **工具沙箱**（④）+ **状态机**（⑤）—— 说明 AI 真的能碰业务库、真能改库存，且改不坏。
5. **评测数字**（F5）—— 领域 44% / 域外幻觉 0，主动承认上限，给提升路径。
6. **一次事故复盘**（⑥ 301.8s）+ **一次误判复盘**（① 的 150 vs 171）—— 这两段是"工程能力"的证据，比任何架构图都强。

### 演示动线（评委现场要看的）

1. 门户登录 → 问"XX 仓哪些型号该补货" → 出现富卡片（补货清单 + 数字）。
2. 点卡片「申请调拨」→ **秒级**进建单（讲 B1：这步曾是唯一瓶颈，8~17s，因为把按钮点击当成了自然语言）。
3. 切到 9B00 仓管账号 → 导入串码出库 → 状态变 `OUTBOUND`；再导一次 → **被拒**（讲 ⑤ CAS）。
4. 切 A 仓管 → 确认入库 → `DONE`。
5. 管理台画布删掉 `verify_numbers` → 发布 → **422 + 违规清单**（讲 ②）。
6. 管理台看 token 用量页 → 能看到刚才这几轮的真实消耗（讲 A2/A3）。
