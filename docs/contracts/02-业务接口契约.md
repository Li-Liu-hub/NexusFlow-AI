# 02 · 业务接口契约

> 本文件描述终端 AI 智慧管理平台的 **REST 接口契约**（入参 / 出参 JSON 样例）。
> 所有接口**统一经网关**（`http://49.234.49.192/api/**`）访问，网关做鉴权 + 限流 + 计量。
>
> **网关按 `(path, method)` 精确匹配 `api_db.interface_info`，注册表里没有即返回 403。**
> 登记语句见 `local-init/{61,72,74,78,79,87}-*registry.sql`，当前生效快照见 `db/mysql/10-seed-api_db.sql`。

---

## 一、契约总览

| 前缀 | 归属服务 | 用途 | 鉴权通道 |
|---|---|---|---|
| `/api/terminal/**` | `aismp-agent` | 终端业务：库存、仓位、工单、健康检查、扫描 | 双通道（AK/SK 或 Bearer） |
| `/api/transferOrder/**` | `aismp-agent` | 调拨工单状态机 | 双通道 |
| `/api/agent/**` | `aismp-agent` | 数字员工对话（SSE） | 双通道 |
| `/api/orchestrator/**` | `agent-orchestrator` | 编排层对话入口（SSE） | 门户专用 |
| `/api/admin/**` | `aismp-backend` / `aismp-agent` | 管理面：Agent / Skill / KB / MCP / 审计 / 配额 | 仅 ADMIN |
| `/digitalHuman/**` | `aismp-digital-human` | 数字员工内核：装配、对话、自省 | 双通道 |

### 统一响应包装

除 SSE 外，所有接口返回：

```json
{
  "code": 0,
  "data": { },
  "message": "ok"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | int | `0` = 成功；非 0 = 业务错误码（见下表） |
| `data` | any | 业务载荷，失败时为 `null` |
| `message` | string | 提示文案，失败时可直接展示给用户 |

**业务错误码**（由 `agent` 全局异常处理器统一转换，HTTP 状态仍为 200）：

| code | 含义 | 典型触发 |
|---|---|---|
| `40100` | 未登录 / 身份缺失 | 缺少身份头且无 query 回退 |
| `40300` | 无权限 | 请求仓不在可见范围 / 非 ADMIN 访问 `/admin/**` |
| `40400` | 资源不存在 | 工单号不存在 |
| `40900` | 状态冲突 | 对已 `DONE` 的工单再次确认 |
| `42200` | 业务校验失败 | 库存不足、串码不匹配 |

## 二、身份与数据权限（**所有业务接口的前置约束**）

### 信任根：只能来自网关注入的请求头

网关在转发前会**先剥离客户端伪造的同名头**，再注入真实身份：

| 请求头 | 含义 | 示例 |
|---|---|---|
| `X-User-Id` | 用户 ID | `1024` |
| `X-User-Warehouse` | 用户所属仓码 | `9BZA` |
| `X-User-Role` | 业务角色 | `ACCOUNT_MANAGER` / `WAREHOUSE_KEEPER` |

**下游一律信任注入值**；`?warehouse=` 之类的 query 参数**仅作无头时的回退**，不得作为权限依据。
（此约束对应 §5.15 / §5.16 / §5.23 三批收口，回归见 `deploy/server-secure/_r13/_r14/_r15-*.py`。）

### 可见范围计算

`aismp-agent` 的 `WarehouseScopeResolver` 按 `warehouse.parent_code` **递归**展开该用户可见的仓码集合；
所有查询接口都会校验「请求仓 ⊆ 可见范围」，越权直接 `40300`。

### 演示账号（`api_db.a_user`）

| 账号 | 姓名 | 角色 | 所属仓 |
|---|---|---|---|
| `xn_zg` | 新区账管 | `ACCOUNT_MANAGER` | `9BZA` 东宁市新区分公司（缺货方 / 发起方） |
| `xn_kg` | 新区仓管 | `WAREHOUSE_KEEPER` | `9BZA` |
| `dn_zg` | 东宁账管 | `ACCOUNT_MANAGER` | `9B00` 东宁市分公司（调出方） |
| `dn_kg` | 东宁仓管 | `WAREHOUSE_KEEPER` | `9B00` |

> ⚠️ 真实仓位编码是 **`9B00`（二级库）/ `9BZA`（三级库）**；需求文档里的 `CK01` 是占位符，数据中不存在。

## 三、`/api/terminal/**` 终端业务

### 3.1 库存健康检查

```
GET /api/terminal/health/suggest?warehouseCode=9BZA&top=5
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `warehouseCode` | string | 否 | 缺省用身份头；显式传入需在可见范围内 |
| `top` | int | 否 | 返回条数，默认 5 |

**响应** `data`：

```json
{
  "warehouseCode": "9BZA",
  "warehouseName": "东宁市新区分公司",
  "checkedAt": "2026-10-11T14:00:00",
  "items": [
    {
      "modelCode": "HG6543A",
      "modelName": "运营商光猫 HG6543A",
      "currentStock": 12,
      "waterline": 40,
      "weeklyUsage": 6.5,
      "gap": 28,
      "brandScore": 0.86,
      "donorWarehouse": "9B00",
      "donorAvailable": 156,
      "suggestion": "从 9B00 调拨 28 台"
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `gap` | 缺口 = `max(waterline - currentStock, 0)` |
| `brandScore` | 品牌兼容评分 0~1，用于选调出仓 |
| `donorAvailable` | 调出仓可用量（已扣在途） |

> **数字红线**：以上字段全部来自 `tools/algorithms.py` 的确定性计算 + 纯 SQL 聚合，**不经过 LLM**。

### 3.2 补货/调拨建议预览（编排层同口径入口）

```
POST /api/orchestrator/replenish/preview
```

请求：

```json
{ "warehouseCode": "9BZA", "modelCode": "HG6543A" }
```

响应 `data`：

```json
{
  "strategy": "transfer_only",
  "items": [
    { "modelCode": "HG6543A", "gap": 28, "fromWarehouse": "9B00", "canTransfer": 28, "needProcure": 0 }
  ]
}
```

| `strategy` 取值 | 含义 |
|---|---|
| `transfer_only` | 仅调拨可满足 |
| `procure_only` | 仅采购可满足（无富余仓） |
| `mixed` | 调拨 + 采购组合 |
| `""`（空） | 无需补货，`items` 为空数组（**空清单是合法结果**） |

> 与 3.1 走**同一算法**，保证「健康卡」与「对话建议」数字完全一致（§5.17）。

### 3.3 库存告警扫描

```
POST /api/terminal/stockAlert/scan
```

请求：

```json
{ "warehouseCode": "9BZA" }
```

响应：

```json
{ "scanned": 71, "alerted": 1 }
```

- 定时任务 `StockAlertScanner` 每 10 分钟（`terminal.stock-alert.cron` 可覆盖）自动跑一次
- 命中则向 `<仓码>:ACCOUNT_MANAGER` 写一条 `STOCK_ALERT` 通知
- **去重口径**：同仓已有**未读** `STOCK_ALERT` 时只刷新内容，不新增

## 四、`/api/transferOrder/**` 调拨工单状态机

### 4.1 状态机（重构后，§5.21）

```
                    ┌──────────── REJECTED ◄────────────┐
                    │                                   │
APPLIED ──B仓管导入SN确认出库──► OUTBOUND ──A仓管确认入库──► DONE
待确认出库                        已出库(在途)               已完成
   │
   └─── A 账管申请时即可发起
```

| 状态 | 中文 | 说明 |
|---|---|---|
| `APPLIED` | 待确认出库 | 账管已提交，等调出方仓管处理 |
| `OUTBOUND` | 已出库（在途） | 调出方仓管导入串码确认，货已发出 |
| `DONE` | 已完成 | 调入方仓管确认收货，**此时库存才真正 B 减 A 增** |
| `REJECTED` | 已驳回 | 任一环节可驳回，需带理由 |

> **确认链无账管环节**（这是相对初版方案的变更）。

### 4.2 接口清单

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/api/transferOrder/create` | 创建工单（`APPLIED`） |
| `POST` | `/api/transferOrder/send` | 发送给调出方账管 |
| `POST` | `/api/transferOrder/outbound` | 调出方仓管**导入串码**确认出库 → `OUTBOUND` |
| `POST` | `/api/transferOrder/inbound` | 调入方仓管确认入库 → `DONE` |
| `POST` | `/api/transferOrder/reject` | 驳回（带 `reason`） |
| `GET` | `/api/transferOrder/list/page` | 分页查询（**按身份过滤**） |
| `GET` | `/api/transferOrder/detail` | 明细 |

### 4.3 创建工单

```
POST /api/transferOrder/create
```

```json
{
  "fromWarehouseCode": "9B00",
  "toWarehouseCode": "9BZA",
  "items": [
    { "modelCode": "HG6543A", "quantity": 28 }
  ],
  "remark": "库存低于水位线"
}
```

响应：

```json
{
  "code": 0,
  "data": { "orderNo": "TR20261011001", "status": "APPLIED" },
  "message": "ok"
}
```

**四条硬规则**（不满足即 `42200`）：

1. **状态限制**：仅 `APPLIED` 可出库，仅 `OUTBOUND` 可入库
2. **库存充足性**：调出仓可用量 ≥ 申请量
3. **四级仅回退**：调拨方向限「下级 → 上级」或同级的回退场景
4. **跨本地网需审批**：跨本地网调拨需额外审批流

### 4.4 导入串码确认出库

```
POST /api/transferOrder/outbound   (multipart/form-data)
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `orderNo` | string | 工单号 |
| `file` | File | 串码 Excel |

**三重比对**（全部通过才扣库存）：型号匹配 → 数量匹配 → 串码状态 = `可用`。
任一不匹配返回 `42200`，**库存不变**。

### 4.5 库存联动

仅 `DONE` 触发库存变更：`fromWarehouse` 对应型号 `-quantity`，`toWarehouse` `+quantity`，
同时写 `t_stock_movement` 流水。响应：

```json
{ "orderNo": "TR20261011001", "status": "DONE", "movedQty": 28 }
```

## 六、网关登记规则（**最容易踩的坑**）

1. **精确匹配，不支持通配回退**：注册的是 `(path, method)` 二元组。已有通配条目
   （`/api/admin/**`、`/api/terminal/**` 等）覆盖这些前缀，**新增前缀必须单独登记**。
2. **门户 Bearer 通道同样校验 `interface_info`** —— 不是只有 AK/SK 通道才校验。
   漏登记的现象是 **403，而不是 404**，容易被误判为鉴权问题。
3. **列名是 `url` 不是 `path`** —— 查 `interface_info` 时若用 `path` 列会**静默返回空**（不报错），
   曾因此得出「没有登记」的错误结论。
