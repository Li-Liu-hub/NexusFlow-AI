# 知识库问答评估报告（M3）

> 评估对象：终端 AI 智慧管理平台 · 知识问答路线
> 评估时间：2026-10（数据见 `agent-orchestrator/docs/m4_eval_pass{1,2,3}.*`）
> 评估集：20 题，覆盖 5 种题型
> 数据口径：**关键词命中率（客观锚）+ LLM 判官合格率（主观分）双口径**

## 一、结论速览

| 指标 | 第 1 遍 基线 | 第 2 遍 自纠环 | **第 3 遍 正式提示词** |
|---|---|---|---|
| 关键词命中率 | 57.1% (32/56) | **91.1% (51/56)** | **92.9% (52/56)** |
| 全命中题数 | 11/20 | 17/20 | **18/20** |
| 零命中题数 | 8 | 2 | **2** |
| 判官合格率 | 50.0% (10/20) | **90.0% (18/20)** | 85.0% (17/20) |
| 触发回炉题数 | — | 9 | 8 |
| 降级放行题数 | — | 2 | 3 |
| 平均单题耗时 | 97.8s | 154.9s | 125.4s |
| 执行异常题数 | 0 | 0 | 0 |

**核心结论**：

1. **自纠环（critic）带来决定性增益**：关键词命中率 **57.1% → 91.1%（+34.0pp）**，判官合格率 **50.0% → 90.0%（+40.0pp）**。这是本项目「质检闸门」价值最直接的量化证据。
2. **代价是耗时**：平均单题从 97.8s 升到 154.9s（**+58%**），因为 9/20 题触发了回炉重跑。第 3 遍优化提示词后回落到 125.4s，且命中率仍略升（92.9%）。
3. **第 3 遍 vs 第 2 遍**：命中率微升（+1.8pp）、判官合格率微降（-5.0pp），属单题级别的波动（1 题差异），二者应视为**同一水平**。第 3 遍在耗时上更优，故作为最终口径。

## 三、失败案例归因（第 3 遍，2 题未达标）

### 案例 1：ID 4 ·「电费稽核是什么流程」（简单事实，命中 0/3）

| 维度 | 内容 |
|---|---|
| 现象 | 关键词零命中，判官判定**不合格（答非所问）** |
| 期望 | 说明电费稽核全流程（工单发起 → 审核 → 审批 → 归档） |
| 根因 | **知识库无对应文档** —— 操作手册中没有「电费稽核」章节，检索层拿不到依据 |
| 定性 | **内容缺口，非技术缺陷**。检索、生成、质检三段均正常工作（critic 已尝试回炉 1 次后降级放行） |
| 处置 | 补文档即可解决；或从评估集中移除超范围题目 |

### 案例 2：ID 18 ·「今天天气怎么样」（超纲，命中 0/0，判官不合格）

| 维度 | 内容 |
|---|---|
| 现象 | 系统礼貌拒答 + 提示服务范围 + 给替代建议，判官判**不合格**（理由：未提供天气信息） |
| 实际 | **这是模型应有的正确行为** —— 系统是终端业务助手，本就不该答天气 |
| 根因 | **判官口径过严**：判官 prompt 要求「非拒答且内容相关」，未对「超纲题」开设豁免 |
| 定性 | **评估口径缺陷，非系统缺陷**。该题应记「合格」 |
| 处置 | 判官 prompt 增加规则：*若问题超出系统业务范围，礼貌拒答并说明范围 = 合格* |

> 修正案例 2 后，第 3 遍判官合格率应为 **18/20 = 90.0%**，与第 2 遍持平。

## 四、评估方法说明

### 双口径设计

| 口径 | 实现 | 优点 | 局限 |
|---|---|---|---|
| **关键词命中率** | 评估集每题带 `keywords`，纯字符串匹配回答 | 零 LLM 调用、完全客观可复现 | 只测「是否提到」，不测「是否答对」 |
| **LLM 判官合格率** | 独立 LLM 按「非拒答 + 内容相关 + 结论正确」三判据打分 | 能识别答非所问、拒答 | 判官自身有口径偏差（见案例 2） |

两口径**互补**：关键词命中率高但判官低 = 答非所问；关键词低但判官高 = 表述差异但意思对。

### 执行细节

- 每题独立会话（`conversation_id` 唯一到「遍次 × 题目」），**防止跨题记忆污染**
- 并发 5 路（8 路会触发模型端限流长尾，实测降到 5 路换干净数据）
- 单题异常不中断整遍，记 `error` 行便于统计
- 原始数据全留痕：`m4_eval_pass{N}.csv`（人读明细）+ `_answers.jsonl`（回答全文）+ `_judged.jsonl`（判官结论）

### 复现命令

```bash
cd agent-orchestrator
# 第 1 遍：基线（critic 关闭）
uv run python scripts/m4_eval.py 1
# 第 2 遍：自纠环（critic 开启）
uv run python scripts/m4_eval.py 2
# 第 3 遍：正式提示词
uv run python scripts/m4_eval.py 3
# 判官打分
uv run python scripts/m4_judge.py <pass_n>
```

> ⚠️ 脚本 `m4_eval.py` 内的 `EVAL_SET` 曾硬编码外部绝对路径，已于本次修正为**项目内相对路径**（见 `scripts/m4_eval.py`）。

## 六、RAG 准确率专项评测（新增，与上文互补）

上文（M3/M4）测的是**整条编排链**（改写 / 路由 / 自纠环）在 20 题上的关键词命中率。
本节是一套**专门测 RAG 检索与回答准确率**的评测，两者口径不同、互不替代。

### 6.1 为什么另做一套

| 维度 | 上文 m4_eval（编排链） | 本节 rag_accuracy_eval（RAG） |
|---|---|---|
| 关心什么 | 链条整体是否走对、自纠环是否有效 | 检索是否命中、回答是否答对 |
| 判分 | 关键词命中 + LLM 判官 | **三口径**：召回 / 要点覆盖率 / 严格准确率 |
| 超纲题 | 混在分母里（曾因此误判，见第三节案例 2） | **单独统计拒答率 / 幻觉率，不进准确率分母** |
| 测试集 | `eval-set.json`（20 题） | `aismp-qa-eval.json`（22 题）+ `aismp-qa-oob.json`（20 题域外基线） |

### 6.2 准确率三口径（层层递进）

单看「关键词命中率」会高估——废话里也可能带关键词。故分三层：

1. **召回 Recall** = 回答中出现的关键词数 / 题目给定关键词总数，用来反推**是否检索到了预期文档**
   （回答不返回 doc_id，只能靠文档级特征词反推）。
2. **要点覆盖率 Point Coverage** = 每条 `answer_points` 的判定词是否在回答里出现，比例取平均。
   **这是最接近「答得对不对」的指标**。
3. **严格准确率 Strict Acc** = 要点覆盖率 ≥ 阈值（默认 0.6）的题数 / 有效题数。
   **这就是要写进比赛报告的「准确率」主数字。**

### 6.3 超纲题 = 拒答率 / 幻觉率（关键设计）

超纲题**不能混进准确率分母**，否则会把「正确拒答」当成「答错」。本套评测单独统计：

- **正确拒答**：回答含兜底话术（`知识库暂时不可用` / `无法回答` / `超出` 等）→ 记合格。
- **⚠️ 幻觉**：该拒答却自称「根据知识库/文档」给出具体内容 → 这是要重点盯的**坏指标**。

### 6.4 域外基线（DuReader 风格）

`aismp-qa-oob.json` 内的 20 题照搬 **DuReader-Retrieval**（百度开源通用检索集）的风格
——通用网页领域（"太阳花怎么养" 之类），**与本站业务知识毫无重合**。

跑它的预期是 **Recall≈0**。价值不在分数低，而在于给出**对照**：
> 「同一套系统在领域题上 X%，在通用题上 0%」——这个对比才能证明**题目选对了**，
> 而不是系统不行。这也正是**不能直接拿 DuReader-Retrieval 原集测本项目**的量化证据。

### 6.5 ★ 出题必须对齐【真实灌库内容】（踩过的坑）

第一版测试集按 `local-init/kb-seed/*.txt`（31 篇业务语料）出题，`--check` 全过；
但查 PG `vector_store`（25 行）发现**实际灌库的是 `aismp-agent/src/main/resources/faq/**/*.md`（16 篇手册切片）**，
两套语料**完全不重合** → 按 kb-seed 出的题会**全部落空**。

修正后 `CORPUS_DIRS` 只认真实入向量库的 `faq/` 目录，并由 `--check` 逐条验证关键词确实在目标文档正文里。
**改动语料来源后必须重跑 `--check`。**

### 6.6 复现命令

```bash
cd agent-orchestrator
# ① 生成两份测试集（改语料来源后必须重跑）
uv run python scripts/build_rag_eval.py
uv run python scripts/build_rag_eval.py --check     # 校验关键词确实在语料里
# ② 跑领域题（真实准确率，主数字）
uv run python scripts/rag_accuracy_eval.py
# ③ 跑域外基线（预期 Recall≈0，证明题目选对了）
uv run python scripts/rag_accuracy_eval.py --oob
# 可选：严格阈值 / 并发
uv run python scripts/rag_accuracy_eval.py --threshold 0.7 --workers 3
```

产出：`agent-orchestrator/docs/eval/rag_accuracy_{domain,oob}.{csv,jsonl}` + `_summary.json`。

> 评测走**真链路**：编排层 → 网关 → Java RAG 管线 → pgvector，需 5 个 Java 服务与编排层全部启动。

### 6.7 首轮实测结果（2026-10-11，本机全链路，MiMo mimo-v2.6-flash + bge-m3 本地嵌入）

**领域题 22 道（18 道有效 + 4 道超纲），0 运行错误，总耗时 3.7 分钟：**

| 指标 | 数值 | 说明 |
|---|---|---|
| ① 召回 Recall | **86.7%** | 关键词命中/总关键词，反映检索命中面 |
| ② 平均要点覆盖率 | **61.7%** | 最接近「答得对不对」的口径 |
| ③ 严格准确率 Strict | **44.4%**（8/18） | 覆盖率≥0.6 的题占比 |
| 平均耗时 | 27.9s/题 | 三路并发 |
| 超纲 4 题 | **正确拒答 3，疑似幻觉 0** | 天气/改数据库/爬虫/财报类均安全处理 |

**域外基线 20 道（DuReader 风格通用题），0 运行错误，总耗时 2.8 分钟：**

| 指标 | 数值 | 说明 |
|---|---|---|
| 召回 Recall | **0.0%** | 预期行为——知识库里没有通用领域内容 |
| 正确拒答 | **18/20 = 90%** | 2 题越权用 LLM 通用知识作答（「李白是哪个朝代」「5G vs 4G」），但均显式标注「不在业务范围」，0 例伪装成知识库内容 |

**对比结论（本套评测的核心价值）**：同一套系统，领域题召回 86.7% vs 域外题 0% ——
证明**题目对齐了真实灌库语料**，评测分数反映的是系统能力而非题目错配。

**按题型观察（领域题）**：
- **满分题**：盘点职责（1.00）、报表口径（1.00）、串码生成规则（1.00）、0元入库类型（1.00）、终端全生命周期状态（1.00）——术语型/清单型问题表现最好，与 M4 评测「专有名词 100%」结论一致
- **低分题集中在两类**：
  1. **口语化改写**（q6 东西挪仓库 0.50 / q7 串码录错 0.50 / q8 没录终端 0.50）——回答方向对但细节不全
  2. **多意图后半段**（q10 导入注意事项 0.00 / q12 重新分配 0.33）——第一问答得好，第二问常被略过或手册确无对应章节（q13「待智家领用确认」手册真没有，系统如实说明并拒绝推测，**这是正确行为**）

**改进方向（按性价比排序）**：
1. 检索 top-k 扩宽 + 多意图问题拆分（针对 q10/q12 类双问句）
2. 口语化查询的查询重写再强化（q6~q8 均为大白话）
3. q13 类「手册确实没有」的条目，属知识库内容缺口，补文档即解决
