> 定稿时间：2026-10-11
> 适用场景：比赛评审 / 答辩演示
> 演示入口：`http://49.234.49.192/`（门户）、`http://49.234.49.192/admin/`（管理台）
> 全部账号口令统一为 **`123456`**（演示环境，勿用于生产）

## 一、演示目标与叙事主线

**一句话卖点**：把「库存该补了」这件事，从**人工发现**变成**系统主动发现 → AI 给建议 → 数字调到落地**的完整闭环，
且**所有数字都可追溯到确定性的查库与算法，LLM 不参与算数**。

**叙事三段**：

| 段 | 主题 | 要证明的事 |
|---|---|---|
| 第一段 | **被动问答** | 知识库能答业务手册问题（且自纠环提升明显） |
| 第二段 | **主动闭环** | 系统定时发现库存告警 → 建议 → 调拨 → 双角色确认 → 库存真实变动 |
| 第三段 | **平台能力** | 多智能体装配、多租户配额与限流、画布编排、可观测审计 |

**时间预算**：约 18 分钟（含 1 个可选的「恶意消耗被限额拦截」表演）。

## 四、第一段 · 知识库问答（约 3 分钟）

**目的**：展示知识库检索 + 自纠环改造的效果。

### 幕 1.1 · 术语型提问（命中率最高的一类）

**操作**：用 `xn_zg` 登录门户，在对话框输入：

```
密码忘了怎么重置
```

**预期**：回答给出**三种方式**（自助重置 / 联系管理员 / 工单流程），并附锁定规则与密码要求。

**讲解词**：

> 这是知识库问答路线：`supervise` 识别为 `kb` 意图 → 转发数字员工内核 → pgvector 检索手册 → 生成回答。
> 我们的评估集里，专有名词类题目关键词命中率是 **100%**。

### 幕 1.2 · 口语化提问（展示鲁棒性）

**输入**：

```
报表导不出来
```

**预期**：回答覆盖常见原因（数据量超限、任务排队、浏览器拦截等）。

**讲解词**：

> 用户不会按手册说话。口语化类题目命中率 92%，靠的是查询重写 ——
> 「报表导不出来」被改写成「报表导出失败的原因与排查」再去检索。

### 幕 1.3 · 超纲问题（展示边界感）

**输入**：

```
今天天气怎么样
```

**预期**：**礼貌拒答** + 说明服务范围 + 给替代建议（不会胡编）。

**讲解词**：

> 这是刻意的边界。我们的数字员工有明确的服务范围声明，超纲问题直接拒答。
> 顺带说一句：我们的评估里这类拒答一开始被 LLM 判官判成「不合格」——
> 后来发现是**判官口径过严**，已修正为「超纲拒答 = 合格」。

### 📊 此处插入评估数字（关键得分点）

> 我们做了**三遍对照实验**，20 题、5 种题型：
>
> | | 基线（关质检） | **开自纠环** | 正式提示词 |
> |---|---|---|---|
> | 关键词命中率 | 57.1% | **91.1%** | **92.9%** |
> | 判官合格率 | 50.0% | **90.0%** | 85.0% |
> | 平均耗时 | 97.8s | 154.9s | 125.4s |
>
> **自纠环带来 +34 个百分点的命中率提升**，代价是耗时 +58%（部分题触发回炉重跑）。
> 详细报告见 `docs/知识库评估报告.md`。

## 五、第二段 · 补货调拨闭环（**核心，约 10 分钟**）

**目的**：完整走一遍「主动发现 → 建议 → 申请 → 出库 → 入库」，
并**当场验证库存数字真实变动**。

### 幕 2.1 · 系统主动发现库存告警（**最亮的点**）

**操作**：`xn_zg` 登录 → 点击右上角**铃铛**（通知面板）。

**预期**：看到一条**橙色左边条**的「库存告警」通知，内容类似：

> `9BZA` 仓库有 N 个型号低于水位线，建议调拨

**讲解词**：

> 这条告警**不是用户点出来的**。后台 `StockAlertScanner` 每 10 分钟跑一次纯 SQL 聚合，
> 发现低于水位线就主动写通知 —— 用的是和健康检查**完全相同的算法**，没有 LLM 参与。
> 而且去重了：同一个仓已有未读告警时只刷新内容，不会每 10 分钟刷你一遍。

> 💡 **如果演示时没有告警**：点通知面板里的「**扫描本仓**」手动触发，效果一样。

### 幕 2.2 · 点告警 → AI 给建议

**操作**：**点击那条告警**。

**预期**：自动跳转对话、自动提问「补仓推荐师」、流式输出建议，
回答**末尾内嵌一张结构化建议卡**，卡上有两个按钮：**「提交调拨工单」/「暂不处理」**。

**讲解词**：

> 这里触发的是补仓调拨路线：`supervise → fetch → algorithm → report → verify_numbers → critic → respond`。
> 注意 `algorithm` 和 `verify_numbers` 两个节点 ——
> **算法节点用代码算数字**（`tools/algorithms.py`），**校验节点做代码 diff 闸门**：
> 卡片上的数字必须和算法输出**逐字相等**，否则回炉重跑。
> 这就是我们的「数字红线」：**LLM 只决定跑哪个算法、传什么参数，不算数**。

**可以展示「思考过程」折叠区**：里面是节点级的 `progress` 事件，能看到走了哪几个节点。

### 幕 2.3 · 提交调拨申请

**操作**：点建议卡上的「**提交调拨工单**」→ 确认弹窗 → 提交。

**预期**：提示提交成功，跳转到调拨工单页，新工单状态为 **`APPLIED`（待确认出库）**，
卡片上**单号作为第一行主标题**（放大等宽字体）。

**讲解词**：

> 状态机是重构过的：`APPLIED 待确认出库 → OUTBOUND 已出库(在途) → DONE 已完成`，两处可驳回。
> **关键设计：确认链上没有账管环节** —— 账管负责申请，仓管负责实物确认，职责不重叠。
> 现在库存**还没有变**，必须等到最后一步入库确认。

### 幕 2.4 · 切换身份：东宁仓管确认出库

**操作**：**换账号登录** `dn_kg`（东宁仓管，`9B00`）→ 调拨工单页 → 找到待处理工单。

**预期**：工单状态 `APPLIED`，有「导入串码」入口。

**操作**：点「导入串码」→ 上传串码 Excel → 提交。

**预期**：状态变为 **`OUTBOUND`（已出库/在途）**；同时 `xn_zg` 侧收到一条进展通知。

**讲解词**：

> 这一步做了**三重比对**：型号匹配、数量匹配、串码状态必须是「可用」。
> 三个全过才扣库存，任一不匹配直接拒绝且**库存不变**。
> 现在是「在途」状态 —— 货在路上，双方的账都还没动。

> ⚠️ **若浏览器自动化受限上传不了文件**：改为口头说明 + 展示后端已通过 E2E 脚本验证
> （`transfer-flow-e2e.py` 24/24 覆盖了含串码上传的完整链路）。

### 幕 2.5 · 切回：新区仓管确认入库（**库存真正变动**）

**操作**：换账号登录 `xn_kg`（新区仓管，`9BZA`）→ 调拨工单页 → 确认入库。

**预期**：状态变为 **`DONE`（已完成）**。

**⭐ 关键验证动作**：切回 `xn_zg` → 打开库存明细 → 展示该型号**数量增加**；
`dn_kg` 侧对应型号**数量减少**。

**讲解词**：

> **只有到这一步，库存才真正发生变动**：调出仓 `-N`，调入仓 `+N`，同时写一条库存流水。
> 从「系统发现缺货」到「货到入库」，全链路自动化，中间只有两次必要的人工确认 ——
> 一次出库、一次入库，都对应真实的实物动作。

### 幕 2.6 · 展示拒绝分支（可选，30 秒）

**讲解词**：

> 拒绝路径同样完整：任一环节可驳回，**必须填理由**，理由会写进工单并回传给发起方。
> 我们的 E2E 里专门覆盖了「B 仓管拒绝带理由回传 → 第二单同意路径」两种走向。

## 六、第三段 · 平台能力（约 4 分钟）

### 幕 3.1 · 多智能体装配 + 知识库管理

**操作**：`admin` 登录管理台 `/admin/` → 「Agent 管理」页。

**预期**：能看到多个数字员工（如「补仓推荐师」），每个绑定了角色、技能、知识库、工具。

**操作**：切到「知识库」页 → 展示 8 个库、文档列表、切片参数。

**讲解词**：

> 数字员工是**可配置的**：角色人设、挂载哪些技能、绑哪个知识库、能用哪些工具，全在管理面配。
> 知识库的**切片参数按库可配**，嵌入模型只读（防止演示中被改坏）。

### 幕 3.2 · ⭐ 恶意消耗被限额拦截（**表演环节**）

**操作**：用 `dnop04`（**配额已预设为 30000，处于超限状态**）登录门户 → 提问任意问题。

**预期**：**收到「额度用尽」提示卡**，而不是正常回答。

**操作**：切到 `admin` → 「Token 用量」页。

**预期**：看到 `dnop04` 的用量已超配额，**拦截次数 +1**（刚才那次被拦）。

**讲解词**：

> 每个用户有独立的月度 token 配额。调用**前**预检、事后扣减、超额直接拦截，
> 次日自动恢复。这是多租户平台必须有的能力 —— 防止单个用户把额度吃光。
> 管理员在后台能看到实时的拦截次数和用量分布。

### 幕 3.3 · 画布编排（**技术亮点**）

**操作**：管理台 → 「画布编排」页。

**预期**：看到可视化的编排图（节点 + 连线），有**版本管理面板**（草稿 / 已发布 / 历史版本 / 回滚）。

**操作**：点某个节点 → 展示属性面板（可改提示词）；点版本列表的「设为当前」。

**讲解词**：

> 编排逻辑**不是写死在代码里的**，而是画布上的一张图 —— 发布即生效。
> 每个会话在创建时会**固化当时的图版本**，进行中的会话继续用旧版本跑完，
> 不会因为管理员改图而中途换逻辑。回滚的实现是「复制旧版为新的已发布」，历史不篡改。
> 节点库里有 14 个具名节点 + 3 个路由 + 通用的 HTTP 工厂。

### 幕 3.4 · 数据权限（**安全亮点，建议讲**）

**讲解词**：

> 这里有个不太显眼但很重要的设计：**数据权限的信任根在网关**。
> 网关转发前会**先剥离客户端伪造的身份头**，再注入真实身份（用户 ID / 仓码 / 角色）。
> 下游一律信任注入值，`?warehouse=` 这类 query 参数只能作为无头时的回退，**绝不能当权限依据**。
> 我们还做了「层级递归可见范围」：二级库能看到自己下属三级库的数据，反之不行。
> 这套改动的回归测试有 15 项，覆盖了各种越权尝试。

## 七、收尾陈述（30 秒，可直接念）

>
> 1. **把业务做通** —— 从库存告警到调拨入库，全链路闭环，两次人工确认对应两次实物动作。

## 八、应急预案

| 症状 | 原因 | 处理 |
|---|---|---|
| 对话框不出字 | SSE 被代理缓冲 | 检查 nginx `proxy_buffering off`；或用本机环境演示 |
| 上传串码失败 | 浏览器自动化限制 | 口头说明 + 展示 E2E 脚本结果 |
| 没有库存告警 | 定时任务未到周期 | 点通知面板「扫描本仓」手动触发 |
| 提问返回 403 | 接口漏登记网关 | 检查 `interface_info`；**注意列名是 `url` 不是 `path`** |
| 管理台白屏 | 静态资源 base 路径 | 检查 vite `base: '/admin/'` |
| 画布页空白 / 429 刷屏 | 布局发散 / 请求风暴 | 均为已修复问题，若复现请重启管理台 |
| 整体不可用 | 服务器资源 | 该服务器仅 4 vCPU / 3.63GiB，演示时勿同时跑重任务 |
