一、业务痛点

人工运维的四个"靠"

运营商固网终端（光猫、机顶盒、FTTR 等）按省—市—县—网格四级仓储管理，覆盖到智家工程师。 传统模式下面临四个问题：

01
补货凭经验
采购与补货靠个人经验判断，缺乏数据支撑，容易积压或缺货
02
调拨靠电话
跨仓协调依赖线下电话沟通，对方仓有没有货、给多少，全靠反复确认
03
库存靠人工盘查
缺货和长库龄积压靠人工盘查发现，发现时往往已经造成浪费
04
报表手工统计
数据价值沉睡在表格里，管理层看不到终端管理的真实成效
人工方式 vs 平台方式
环节传统人工方式平台化后
补货决策凭个人经验判断，缺乏数据支撑，易积压或缺货确定性算法按周使用量与缺口自动生成补货建议
跨仓调拨电话反复确认对方库存与数量AI统计各区域库存情况，自动生成调拨建议，解决库存不透明问题，平衡区域库存。
库存盘点人工盘查，发现时往往已造成积压浪费定时巡检超警戒线自动告警（10 分钟周期）
数据报表手工统计，数据价值沉睡报表自动生成，补货与调拨全链路留痕可回溯

从人工直觉到数据驱动

六层架构 · 统一网关收口

统一 AI 网关收口 REST API、AI 智能体、MCP 工具的鉴权、限流与 Token 计量； 能注册服务全部走服务发现；Python 编排层经网关签名回调 Java 智能体——跨语言协作、计量全收口

六层各司其职：业务门户与运维台双入口经统一网关收口，Python 编排层与 Java 智能体跨语言互调，计量落账异步解耦

四、编排核心

三智能体协作链 · 模型决策、代码计算

针对大模型在企业场景"编造数字、输出不稳定"的落地障碍， 确立"模型决策、代码计算"的协作边界——LLM 只决定调哪些分析工具，计算全在确定性代码。 三智能体指补货调拨核心链（取数 → 算法 → 报表）；意图识别是前置公共路由， 知识库、图表、质检等能力由画布按场景编排（见第六章）

三智能体职责与协作边界
环节执行者职责输出 / 降级
意图识别AI 智能路由判断用户意图：知识问答 / 补货建议 / 调拨执行，决定工作流分支非业务诉求转入知识库问答兜底
取数取数智能体经网关调用账管服务，按仓位 / 状态 / 型号 / 库龄 / 在途查询库存取数失败即终止并如实提示，禁止用猜测值续算
计算算法智能体确定性算法：周使用量 = 近 3 月日均 × 7，缺口 = 预测需求 −（可用 + 在途），不经大模型同一输入永远得到同一清单，结果可复算
产出报表 / 账管智能体生成采购 / 调拨清单卡片，可导出 Excel，账管一键申请调拨调拨校验不通过原路退回，重新发起
决策边界：模型只做意图识别与工具路由，数字全部出自确定性算法——清单可复算、可审计，杜绝大模型编造数据
