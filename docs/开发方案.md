### 0.2 现有编排层实现（比 v1.0 描述得简单）

```
supervise(LLM 结构化分类) ──┬─ rag    → rewrite → executor → critic ─┬─ respond
```

`graph.py` 现有 8 个函数：`supervise` / `route_after_supervise` / `direct_answer` / `rewrite` / `executor` / `critic` / `route_after_critic` / `on_rework` / `on_degrade` / `respond`。

**修正 ③**：v1.0 文档 M2 要的**三通道（kb / replenish / order）+ 8 节点 + strategy 三态 + 数字 diff 双闸门，全部是新写**。可沿用的资产是：SSE 事件协议、`merge_dict` reducer、`get_stream_writer()` 旁路推流模式、`tools/java_agent.py` 的网关签名调用范式。

### 0.6 安全基线（重要）

**2026-09-30 这台服务器被入侵了**，完整取证与加固方案见 `deploy/server-secure/README.md`。摘要：

| 项 | 事实 |
|---|---|
| 入口 | MySQL `root`/`123456` + `root@'%'` 公网开放；Redis 无密码 + `bind 0.0.0.0` |
| MySQL 后果 | 所有库被 `DROP`（含 `api_db`），留下勒索库 `RECOVER_YOUR_DATA` |
| Redis 后果 | 被写入 4 个后门 key，指向恶意域名 `kiss.a-dog.top` |
| PostgreSQL | **未被破坏**（运气，不是安全） |
| SSH | 无后门，但累计 **5594 次**爆破尝试 |
| 真实业务数据 | **无损失**（28354 条只在本机 xlsx） |

**处置（已确认）**：重装系统 → 跑 `deploy/server-secure/90-harden.sh` 加固 → 保持对外服务但**数据库不对公网暴露**。

## 二、目标架构（改造后）

> **2026-10-06 架构重构**（本图已同步更新，旧版图缺内核层且业务位置错误）：
> ①业务实现（终端库存/调拨）从 backend 迁到 **aismp-agent**，backend 只留平台管理（用户/接口/鉴权）；
> ②编排层（Python）只管"走哪条链路"，不做业务；
> ③**aismp-digital-human 内核**只提供 agent 能力（装配数字员工 + ReAct 循环）；
> ④全部 Java 服务注册 **Nacos 3.2.4**，网关路由一律 `lb://`（不再写死 IP）；
> ⑤版本统一到 **Spring Boot 4.0.7 + JDK 21**。

```
开发者 / 前端
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ aismp-gateway :8090    鉴权（AK/SK + Bearer）→ 限流 → 计量    │
│ 路由全部 lb://（Nacos 服务发现；Python/Mock 两个例外是静态）  │
└─────────────────────────────────────────────────────────────┘
        ├─► /api/terminal/** · /api/transferOrder/**  → lb://aismp-agent :8124   【终端业务】
        │        StripPrefix=1；业务实现在 agent（api_db：terminal/warehouse/transfer_order）
        │        GET  /terminal/inventory/{aggregate|aging|snapshot|byModel|serialNos}
        │        GET  /terminal/stat/cards · /terminal/warehouse/list
        │        POST /transferOrder/{create|outbound|inbound|reject}
        │        GET  /transferOrder/{get|list/page}
        │        （登记见 local-init/72-terminal-route-registry.sql）
        │
        ├─► /digitalHuman/**                          → lb://aismp-digital-human :8126 【数字员工内核】
        │        POST /agent/{code}/chat              运行面：装配数字员工 + ReAct + 工具调用
        │        POST /agent/{code}/introspect        运行时自省（装配了什么）
        │        POST /admin/agent/**                 配置面：新建数字员工/挂工具/挂知识库（零代码）
        │        └─ 知识检索工具再回调 agent 的 RAG 能力（HTTP + AK/SK）
        │
        ├─► /oa/** · /sse · /mcp/**                   → lb://aismp-agent :8124   【RAG / MCP】
        │        POST /oa/chat/sync（编排层 rag 通道；内核知识检索也走它）
        │
        ├─► /orchestrator/v1/chat/stream              → agent-orchestrator :8125  【核心编排】
        │        静态 uri（Python 暂不注册 Nacos）
        │        LangGraph 三通道：kb(→数字员工) / replenish / order
        │        supervise → [digital_human | fetch→algorithm→report→verify→critic | order] → respond
        │
        └─► /api/**（其余）                            → aismp-interface :8123（Mock，静态 uri）
        │
        ▼ 计量链路：网关 → RabbitMQ → backend 消费 → MySQL（token 账本 M4）
                   网关 → backend /api/inner/**（用户/接口信息，HTTP + lb://）为鉴权链供数
```

**接入方实际走向**（与"一切经网关"的直觉不同，2026-10-06 实测）：

| 接入方 | 实际走向 |
|---|---|
| 用户门户 5173 | vite/nginx 代理**直连内核 8126**（`/api` → 8126） |
| 管理台 5174 | 同上直连内核（配置面）；backend 的 `/admin/digitalHuman/**` 代理是"登录态+角色"把关的备选通道 |
| 编排层 8125 | **走网关**（AK/SK + Bearer），终端业务与数字员工都经网关 |
| backend 7529 | 网关鉴权链经 `/api/inner/**` 调用（HTTP + lb://aismp-backend）；前端登录态接口直连 |

### M2 · 调拨工作流（编排层，技术含量最高）

**落点**：`agent-orchestrator/graph.py`（296 → 预计 700+ 行）

**三通道 × 8 节点**：

| 节点 | 本质 | 改法 |
|---|---|---|
| `supervise` | LLM 结构化分类，三值 `kb / replenish / order` | 改 `RouteDecision` 的 `Literal`；`ROUTE_PROMPT` 换终端域 few-shot |
| `rag_node` | **纯转发**：经网关调 Java `/oa/chat/sync` | 由现有 `rewrite + executor` 合并简化（知识库换终端手册后，重写提示词换终端域） |
| `fetch` | 取数智能体，工具循环 ≤3 轮 | **全新**。4 个工具：`inventory_aggregate` / `terminal_detail` / `aging` / `intransit` |
| `algorithm` | 算法智能体 + 确定性工具箱 | **全新**。5 件分析工具：`weekly_usage` / `gap` / `waterline` / `transfer_feasibility` / `brand_score`。**LLM 只决定跑哪几种、传什么参数，数字全在代码里算** |
| `report` | 报表生成：装卡片 → `verify_numbers` 自检（≤2 轮）→ 总结句 | **全新**。输出 `cards` + `suggestion_id`（建议结果存 Redis，30 分钟） |
| `order` | 建单智能体，工具循环 ≤3 轮；双入口 | **全新**。工具：`create_order` / `parse_excel`；先重校验库存再建单 |
| `critic` | **双闸门**：① 代码 diff 卡片数字 === 算法输出 ② LLM 语义合理性 | 改造现有 `critic`，增加确定性 diff 检查；**按失败类型分流回炉**（数字不一致→回 report；取数不全→回 fetch；kb/order 语义不合格→降级放行） |
| `respond` | 纯组装 | 改造：输出 `cards` 数组 + token 汇总 |

**State 扩展**（`state.py`）：新增 `inventory_snapshot` / `algo_result` / `strategy` / `cards` / `suggestion_id` / `order_info`；`route` 改三值。

**关键机制**：限额预检前置（每个 LLM 节点调用前查 backend 余额）、两段式人工确认（不引入 `interrupt`）、`strategy` 三态驱动卡片渲染（`transfer_only` / `procure_only` / `mixed`，空清单合法）。

## 七、服务器重建与安全加固

**完整手册见 `deploy/server-secure/README.md`**，这里只放结论。

### 处置方案（已确认）

重装系统 → 加固 → **保持对外提供服务，但数据库不对公网暴露**。

### 你要在控制台做的（只有你能做）

1. 轻量应用服务器 → 实例 `lhins-efltpzqo8` → **重装系统** → `Ubuntu 24.04 LTS` → 设置**强密码**
   （别去 CVM 安全组页面找，轻量应用服务器用的是「防火墙」，两个入口不互通）
2. 防火墙规则**保持不动**（按你的要求）
3. 重装后公网 IP 不变，但登录密码变了 → 我要改 `D:\env\ssh_helper.py` 里的 `PASSWORD`

### 加固做了什么（重装后由 `90-harden.sh` 自动完成）

| 组件 | 加固前（被打穿的状态） | 加固后 |
|---|---|---|
| MySQL | `root`/`123456` + `root@'%'` 全权限 | `root` 只留 localhost；应用改用 `api_user`，**只授权 `api_db`** |
| PostgreSQL | `my_user`/`123456`，`pg_hba` 放行所有库 | 强密码；**只允许从外部连 `terminal_kb`** |
| Redis | 无密码 + `protected-mode no` | 强密码 + `protected-mode yes` + **封掉 `CONFIG`/`FLUSHALL`/`SLAVEOF`/`DEBUG`** |
| RabbitMQ | `guest`/`guest` 且允许非本机登录 | 专用用户 `aismp` + 强密码，**删除 `guest`** |
| Nacos | 无鉴权（任何人能改注册表） | `auth.enabled=true` + token secret + server identity |
| SSH | 裸露（已尝试爆破 5594 次） | **fail2ban**：10 分钟失败 5 次封 1 小时 |
| 本机防火墙 | 无 | **ufw**：默认拒绝入站，只放行 22 + 应用端口 |

**关于"不改控制台"**：数据库端口收口在 **ufw** 里做，不影响你说的"对外公开"——
对外公开的是**应用**（8000 等），数据库走 localhost。既然应用也在同一台机器上，数据库根本不需要对外。
需要本机直连调试时用 SSH 隧道：
```bash
ssh -L 13306:127.0.0.1:3306 -L 15432:127.0.0.1:5432 ubuntu@49.234.49.192
```

## 八、服务器内存预算（必须先解决，否则部署完就 OOM）

实测 `free -m`（2026-10-01）：

| 项 | 数值 |
|---|---|
| 总内存 | **3659 MB** |
| 已用 | 2060 MB |
| **可用** | **1598 MB** |

中间件实测占用：**Nacos 873MB** / MySQL 357MB / RabbitMQ 141MB / PostgreSQL 30MB / Redis 14MB，
另加腾讯云自带 agent（云镜 + barad 约 134MB）与 dockerd+containerd（144MB）。

全量部署应用后的估算（已按最省的方式算）：

| 服务 | 限内存参数 | 估算 RSS | 备注 |
|---|---|---|---|
| aismp-backend | `-Xmx256m` | ~350 MB | |
| aismp-gateway | `-Xmx256m` | ~300 MB | WebFlux，Nacos 客户端常驻 |
| aismp-agent | `-Xmx512m` | ~600 MB | Spring Boot 3.5 + Spring AI，压不下去 |
| agent-orchestrator | — | ~150 MB | Python |
| 前端（**静态托管**） | — | ~20 MB | 绝不能跑 `max dev`，开发模式要 500MB~1GB |
| **小计** | | **~1420 MB** | |
| 加上已占用的中间件 2060 MB | | **~3480 MB** | vs 总内存 3659 MB |

**结论：纸面上刚好塞满，实际会因为页缓存、GC 峰值、突发流量而随机 OOM Kill。**

### 三个可选做法

| 方案 | 省出 | 代价 |
|---|---|---|
| **A. 升配到 4C8G（推荐）** | 一步到位 | 轻量应用服务器支持在线升配，按月加钱 |
| B. 不部署 `aismp-interface`（8123 Mock 服务） | ~250 MB | v1.0 文档 2.1 已注明"比赛可不用 interface" ——⚠️ 但网关 `interface_info` 表里登记了它的路径，`e2e-test.mjs` 第 1 项就是打它 |
| C. 砍 Nacos + Dubbo 改 HTTP | ~873 MB | **改动大**：网关 `CustomGlobalFilter` 有 3 处 `@DubboReference`、`AismpGatewayApplication` 1 处，等于重写鉴权链路 |

**另外必须做**：把 swap 从 1987MB 加大到 4096MB 作为兜底（`/swapfile`），避免直接 OOM Kill。
但这只是保险，不能替代内存。
