## 一、先决判断：不升级 Spring AI

| 方案 | 代价 | 结论 |
|---|---|---|
| 升级到 Spring AI 1.1.2 + SAA 1.1.2.2 | 牵动已跑通的 kb 通道（历史踩过 `BaseAdvisorCallAdapter` 的坑，1.1.x advisor 机制又变） | ❌ 暂不 |
| 保持 Spring AI 1.0.3，自实现 `ToolCallback` | 新增代码，不动存量 | ✅ 采用 |

**依据**：Spring AI 1.0.3 的 `org.springframework.ai.tool.ToolCallback` 是接口，
`getToolDefinition()` / `call(String)` 均可自行实现。声明式工具（SQL 模板）不需要框架支持。

SAA 留作后续可选项：等 P1~P3 跑通、版本升级单独验证后，再考虑接 `starter-config-nacos` 做 Nacos 热更新。

## 三、数据模型（P1）

在 `terminal_db` 新增 3 张表，**不改动任何已有表**。

```sql
-- 1. 数字员工定义（核心）
CREATE TABLE `a_agent` (
  `id`                bigint       NOT NULL AUTO_INCREMENT,
  `agent_code`        varchar(64)  NOT NULL COMMENT '数字员工编码，运行时按它装配',
  `agent_name`        varchar(128) NOT NULL COMMENT '显示名',
  `avatar`            varchar(255)          DEFAULT NULL COMMENT '头像 URL',
  `description`       varchar(500)          DEFAULT NULL COMMENT '一句话介绍',
  `system_prompt`     text         NOT NULL COMMENT '人设提示词（基底）',
  `model_name`        varchar(64)  NOT NULL DEFAULT 'mimo-v2.6-flash',
  `temperature`       decimal(3,2) NOT NULL DEFAULT 0.70,
  `max_turns`         int          NOT NULL DEFAULT 10 COMMENT 'ReAct 最大轮次',
  `knowledge_base_id` bigint                DEFAULT NULL COMMENT '绑定知识库 → a_knowledge_base.id',
  `status`            varchar(16)  NOT NULL DEFAULT 'active',
  `version`           int          NOT NULL DEFAULT 1 COMMENT '配置版本号，任何变更 +1（P2 热更新依据）',
  `tenant_code`       varchar(32)           DEFAULT NULL,
  `create_time`       datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`       datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_agent_code` (`agent_code`),
  KEY `idx_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='数字员工定义';

-- 2. 技能包（提示词片段 + 示例，可跨数字员工复用）
CREATE TABLE `a_agent_skill` (
  `id`              bigint       NOT NULL AUTO_INCREMENT,
  `skill_code`      varchar(64)  NOT NULL,
  `skill_name`      varchar(128) NOT NULL,
  `description`     varchar(500)          DEFAULT NULL,
  `prompt_fragment` text                  DEFAULT NULL COMMENT '追加到 system_prompt 之后',
  `examples`        text                  DEFAULT NULL COMMENT 'Few-shot 示例（JSON 数组）',
  `status`          varchar(16)  NOT NULL DEFAULT 'active',
  `create_time`     datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`     datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_skill_code` (`skill_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='技能包';

-- 3. 两条挂载关系（多对多 + 顺序）
CREATE TABLE `a_agent_skill_rel` (
  `agent_id`   bigint NOT NULL,
  `skill_id`   bigint NOT NULL,
  `sort_order` int    NOT NULL DEFAULT 0,
  PRIMARY KEY (`agent_id`, `skill_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='数字员工-技能 挂载';

CREATE TABLE `a_agent_tool_rel` (
  `agent_id`   bigint NOT NULL,
  `tool_id`    bigint NOT NULL COMMENT '→ a_llm_tool.id',
  `sort_order` int    NOT NULL DEFAULT 0,
  PRIMARY KEY (`agent_id`, `tool_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='数字员工-工具 挂载';
```

**关键设计**：`version` 字段是 P2 热更新的支点。任何配置变更（含挂载关系变动）都 +1，
运行时缓存用它判断是否需要重建，无需重启。

## 四、运行时装配（P2）

### 装配流程

```
AgentAssembler.assemble(agentCode)
  1. 查 a_agent                          → system_prompt / model / temperature / max_turns
  2. 查 a_agent_skill_rel ⋈ a_agent_skill → 按 sort_order 拼接 prompt_fragment 与 examples
  3. 查 a_agent_tool_rel  ⋈ a_llm_tool   → 为每条工具构造 SqlTemplateToolCallback
  4. 组装 ChatClient（system prompt + tools + 会话记忆）
  5. 返回 AssembledAgent{ version, chatClient }
```

### 缓存与热更新

```
Map<String, AssembledAgent> cache   // key = agent_code

get(agentCode):
    latest = SELECT version FROM a_agent WHERE agent_code = ?
    cached = cache.get(agentCode)
    if (cached == null || cached.version != latest) → 重建并替换
    return cached
```

**为什么用查库而不是监听**：本机无 Nacos，且数字员工定义是低频变更、高频读取。
查一次 `version`（主键索引，微秒级）比维护监听链路简单可靠。
`version` 比对而非 `update_time` 比对，避免"改了但内容没变"造成的无谓重建。

同时提供 `POST /admin/agent/{code}/reload` 手动刷新，便于演示时立刻看到效果。

### 关键类

| 类 | 职责 |
|---|---|
| `SqlTemplateToolCallback implements ToolCallback` | **P3 核心**：把一条 `a_llm_tool` 记录变成可被 LLM 调用的工具 |
| `AgentAssembler` | 按 agent_code 装配出 ChatClient |
| `AgentRegistry` | 装配结果缓存 + version 比对 + 手动刷新 |
| `AgentAdminController` | 数字员工/技能/挂载的增删改查接口 |

## 五、查库工具（P3）

### SqlTemplateToolCallback 的执行链路

```
LLM 决定调用工具 queryStockByLocation
        │  {"locationName": "西湖"}
        ▼
1. 解析 JSON 入参
2. 参数名白名单校验（只允许 input_schema 里声明的参数，防注入）
3. 渲染 sql_template：把 :locationName 替换为命名参数
4. 安全闸门（三重）
   ├─ SQL 必须以 SELECT 开头（拒绝 DML/DDL）
   ├─ 禁止分号后的第二条语句
   └─ 强制追加 LIMIT result_limit
5. 租户隔离：若配了 table_alias，自动注入 tenant_code 条件
6. JdbcTemplate 执行（只读账户）
7. 结果转 JSON 返回给 LLM
8. 写 a_tool_call_log
```

### 三重安全闸门的重要性

这是整个设计里**最不能省的部分**。让 LLM 生成的 SQL 直接执行，风险从"答错"升级为"删库"。
三道门分别防：**写操作**、**多语句注入**、**全表扫描拖垮数据库**。
配合数据库层的**只读账户**，构成纵深防御（与应用层的 `SELECT` 校验互为兜底）。

## 六、任务拆解与验收

| 阶段 | 任务 | 验收标准 |
|---|---|---|
| **P1** | 建 3 张表 + 写入 1 个数字员工种子数据 + 实体/Mapper/CRUD 接口 | `POST /admin/agent/list` 能返回数字员工；改 `system_prompt` 后查询能看到新值 |
| **P2** | `AgentAssembler` + `AgentRegistry` + 缓存 | 改配置 → **不重启** → 问同一问题，回答随人设变化 |
| **P3** | `SqlTemplateToolCallback` + 挂载 `a_llm_tool` 里的工具 | 问"西湖有哪些终端" → agent 自主选工具 → 返回**真实库数据** |
| **终验** | 端到端 | 新建一个数字员工 → 挂 2 个工具 → 直接对话即可查库，**全程零 Java 改动** |

### 最小可信闭环

P1~P3 做完的效果：**在数据库里插一行工具定义 + 建一条挂载关系，数字员工立刻就会用它查库。**
这足以证明"内核可配置"成立，也是给评委演示的最有力场景。

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| LLM 生成/选择错误工具 | 工具 `tool_desc` 写清适用场景（已有的 19 条描述质量不错，可直接用） |
| SQL 注入 | 三重闸门 + 只读账户 + 参数白名单 |
| 数字员工配置改坏导致线上异常 | `status` 字段可停用；装配失败降级到默认人设而非抛错 |
| 本机与服务器数据不一致 | P1~P3 用本机 `terminal_db`（500 条 demo 数据）验证机制，上线前再导真实数据 |
| 工具太多导致 LLM 选错 | 单个数字员工挂载工具数建议 ≤ 8，超出时按场景拆数字员工 |
