## 二、可以优化的地方（按「收益 ÷ 风险」排序）

### 2.1 ⭐ Python 编排层 437 MB → 碎片化，改一个环境变量就能回收

**证据（都是实测）**
```
VmRSS: 471 MB   Threads: 3   VmData: 642 MB
Pss_Anon: 451 MB        SwapPss: 142 MB   ← 1/3 已被换出到磁盘
pmap 最大匿名映射： 87MB / 65MB / 63MB / 60MB / 45MB / 41MB   ← 6 个 64MB 级块
site-packages 仅 141MB（无 torch/onnx，排除模型占用）
二次采样 5 秒：456.27 MB → 456.27 MB（不涨）→ 不是正在泄漏，是历史碎片
```
**诊断**：只有 **3 个线程**，却有 **6 个 40–87MB 的匿名映射**，这是 **glibc malloc arena 碎片化**的教科书特征。
glibc 为每个线程建一个 arena，每 arena 以 **64MB 为粒度** mmap 且**几乎不归还**；`langgraph`/`httpx`/`tiktoken`
在运行期反复创建销毁线程（`anyio` 线程池），arena 就永久留在地址空间里。

**做法**（改 drop-in，不动 ExecStart）
```ini
# /etc/systemd/system/agent-orchestrator.service.d/10-memory.conf
[Service]
Environment=MALLOC_ARENA_MAX=2
```
**预期回收：150–250 MB** ｜ 风险：极低（3 线程场景下对 malloc 吞吐无感知）
**顺带**：venv 里装了 `pytest / _pytest / pluggy / iniconfig`（生产不需要），可 `pip uninstall` 掉——只省磁盘，不影响内存。

### 2.2 ⭐ 4 个业务 JVM —— 堆用得极少，但 code cache 预留 240MB

**实测（`jcmd GC.heap_info` / `Compiler.codecache`）**

| 服务 | 堆 committed | 堆 used | Metaspace used | code cache used | **code cache 预留** | 线程 |
|---|---:|---:|---:|---:|---:|---:|
| gateway | 89 MB | **36 MB** | 95.7 MB | 23.9 MB | **240 MB** | 74 |
| backend | 92 MB | 80 MB | 90.8 MB | 27.7 MB | **240 MB** | 76 |
| kernel | 90 MB | 62 MB | 77.9 MB | 28.4 MB | **240 MB** | 89 |
| agent | 178 MB | 79 MB | 95.5 MB | 38.4 MB | **240 MB** | 69 |

**可动手的三处**

1. **`-XX:TieredStopAtLevel=1`**（只做 C1 编译，不做 C2）
   → code cache 从 ~24–38MB 降到 ~8–10MB。**每 JVM 省 15–28 MB**，合计 **70–110 MB**。
   这些是低并发管理类服务，不需要 C2 的峰值吞吐。
2. **下调 `-Xmx`**（RSS 跟着 **committed** heap 走，不是 max）
   - `gateway` 256→192（堆只用 36MB，安全）
   - `kernel`、`agent` 384→256（观察到峰值 committed 90/178MB，留 44% 余量）
   - **`backend` 不动**（80/92MB，已接近满，不要碰）
   → 合计 **70–120 MB**
3. **`-XX:+UseSerialGC` 替换 `-XX:+UseG1GC`**
   → 去掉 G1 的并发 GC 线程与记忆集/位图。**每 JVM 省 10–20 MB**，合计 **40–80 MB**。
   代价：Full GC 变全停顿（256MB 堆约 50–200ms），对管理类服务可接受。

> ⚠️ **`-Xss512k` 不要做**：线程栈在 RSS 里只算「已触碰页」（每线程通常 8–24KB），
> 69–89 个线程加起来也就 1–2MB，改 `-Xss` 只影响虚拟地址，**对 RSS 基本无效**。
>
> ⚠️ **`-XX:ReservedCodeCacheSize` 单独调小没用**：预留（reserved）不进 RSS，只有 `TieredStopAtLevel=1`
> 才能真正把 code cache 的 **used** 降下来。
>
> ⚠️ **`-XX:MaxMetaspaceSize` 不用动**：committed ≈ used（95.7MB/96.4MB），已贴合实际用量，
> 降它只会导致 `Metaspace OOM`。Metaspace 里那 1.5–1.9 万个类是 Spring 全家桶带来的，**只能改代码，不划算**。

**小计：4 个业务 JVM ≈ 180–310 MB**

### 2.3 Nacos 269 MB —— `Xms=Xmx=256m` 把堆全提交了

```
ExecStart=... -Xms256m -Xmx256m -Xmn128m -XX:MetaspaceSize=96m -XX:MaxMetaspaceSize=128m ...
线程数：321（！）
```
- `-Xms256m` 让 G1 **一开始就提交满 256MB 堆**；改成 `-Xms128m -Xmx192m` 可立即释放一部分
- `-Xmn128m` 在 JDK 17 + G1 下语义已变（G1 下不建议指定新生代固定大小），建议**去掉**
- 再加 `-XX:TieredStopAtLevel=1`

**预期回收：60–110 MB** ｜ 风险：低（单机 standalone 注册中心，无高并发）
> 321 个线程是 Nacos 自身的线程池设计，要改得动它的配置，**收益/麻烦比不划算，不做**。

### 2.4 PostgreSQL —— 10 个 idle 连接

```
pg_stat_activity: 8 个其他 + 1 active + 10 idle      ← 每连接 ~15MB RSS
shared_buffers = 96MB（已手动降过，默认 128MB，保持）
idle_session_timeout = 0（等于关闭）
```
**做法**：`ALTER SYSTEM SET idle_session_timeout = '5min';` 后 reload（不用重启）。
或改客户端 HikariCP 的 `minimum-idle` / `maximum-pool-size`。

**预期回收：30–50 MB** ｜ 风险：极低
> 注意：`shared_buffers` **不要为省内存而调大**，也不要动——PG 总占用才 ~40MB，收益小、风险大。

### 2.5 关闭云主机上无意义的守护进程

实测**正在运行**且对本机毫无用途的：

| 服务 | 状态 | 为什么能关 |
|---|---|---|
| `multipathd` | active/enabled | root 在 `/dev/vda3`，无多路径存储 |
| `ModemManager` | active/enabled | 云主机没有蜂窝模块 |
| `udisks2` | active/enabled | 无桌面环境 |
| `apport` | active/enabled | 崩溃上报，无人看 |
| `sysstat` | active/enabled | 有 `systemd-cgtop`，用不上 sar |
| `fwupd` | active/**static** | 云主机不刷固件（需 `mask`，`disable` 对 static 无效） |
| `upower` | active/disabled | 无电池（需 `mask`） |

**预期回收：50–90 MB** ｜ 风险：极低

**❌ 不要动**：`unattended-upgrades`（安全更新）、`fail2ban`、`ufw`、云镜 `YunJing`（**服务器被入侵过一次，
HIDS 值得留那 41MB**）、`stargate/sgagent`（腾讯云控制台的监控曲线靠它）。

### 2.6 ⭐ 白扔的 192 MB —— `crashkernel` 预留（需重启）

```
/proc/cmdline: ... crashkernel=0M-3G:0M,3G-8G:192M,8G-16G:256M,...
/sys/kernel/kexec_crash_size = 201326592 = 192 MB
```
内核按「物理内存 4GB 落在 3G–8G 区间」预留了 **192MB** 给 kdump 的崩溃内核。
云主机根本用不到这个（崩溃内核内存你既看不到也取不出来），`kdump-tools` 还是 enabled。

**做法**
```bash
sudo systemctl disable --now kdump-tools
sudo sed -i 's#crashkernel=[^ ]*##' /etc/default/grub
sudo update-grub
# 重启后 MemTotal 3.63GiB → 约 3.82GiB
```
**预期回收：192 MB** ｜ 代价：**需要重启一次服务器**（这也是为什么单独放一档）
> ⚠️ 腾讯云 cloud-init / tat 有可能在下次开机把 `crashkernel=` 写回去，重启后需复查 `/proc/cmdline`。

| 1 | Python 编排层 `MALLOC_ARENA_MAX=2` | 150–250 MB | 极低 | 否（重启该服务） |

| 1 | PG `idle_session_timeout=5min` | 30–50 MB | 极低 | 否（reload） |

## 四、明确**不做**的事（附理由）

| 方案 | 能省 | 为什么不做 |
|---|---:|---|
| 把 4 个 JVM 合并成 1 个 | 500–700 MB | 每个 JVM 固定开销≈200MB，合并确实最省；但会**摧毁「网关 / 内核 / 后端 / 数字人」的微服务架构**，是开发方案的交付物 |
| 删掉 Nacos | 269 MB | 注册中心是架构的一部分 |
| 装 Docker / 1Panel 做可视化管理 | **净增** 150–350 MB | 见 §五；且 1Panel 管不了本机原生服务 |
| 降 `shared_buffers` | <30 MB | 已从 128MB 降到 96MB，PG 总占用仅 ~40MB，再压伤性能 |

## 五、遗留观察项

1. **Python 编排层重启后要观察是否继续爬升**：当前 5 秒采样是平的，但进程已跑 1 天 15 小时。
   `MALLOC_ARENA_MAX=2` 生效后记录基线，隔天对比 `VmRSS`。
2. **`aismp-agent` 降堆后的 Full GC**：若日志出现 `OutOfMemoryError` 或频繁 Full GC，把 `-Xmx256m` 回调到 `320m`。
3. **`available` 的长期走势**：建议在 `60-memory-tune.sh` 之后把 `free -m` 输出留档，一周后对比。
