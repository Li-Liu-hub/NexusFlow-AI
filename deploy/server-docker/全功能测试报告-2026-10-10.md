## 三、❌ 真故障：编排层 3 个接口 500（**同一个根因**）

| 接口 | 结果 |
|---|---|
| `GET /api/orchestrator/v1/conversation/list` | ❌ 500 |
| `POST /api/orchestrator/v1/replenish/preview` | ❌ 500 |
| `POST /api/orchestrator/v1/chat/stream` | ❌ 500 |

**根因**：网关 `application.yml` 的两条路由硬编码了本机回环：
```yaml
- id: orchestrator_route
  uri: http://localhost:8125        # 容器里 localhost = 网关自己的回环
- id: orchestrator_portal_route
  uri: http://localhost:8125
```

**证据（关键）**：500 的响应体是 **Spring 格式**错误 JSON，且**编排层容器日志里完全没有这几条请求** →
**500 由网关产生，不是编排层产生的**。所以「改编排层」不解决问题，**必须改网关的 yml**：

```yaml
uri: ${ORCHESTRATOR_BASE_URL:http://127.0.0.1:8125}
```
+ compose 给 gateway 加 `ORCHESTRATOR_BASE_URL: http://orchestrator:8125`，
**然后重新编译网关并出【新 tag】镜像**（yml 打进 jar，只改 compose 无效）。

> 顺带：编排层的**定时库存巡检曾在网关白名单修复前一直失败**，修复（14:27 上线）后**已完全恢复**。
> 这是「自动化业务任务跨 3 个容器端到端跑通」的铁证：
> ```
> 14:23:25  GET  /api/terminal/inventory/snapshot  → 403 Forbidden   ← 修复前
> 14:33:26  GET  /api/terminal/inventory/snapshot  → 200 OK          ← 修复后 ✅
> 14:33:26  POST /api/transferOrder/notice         → 200 OK          ← 闭环写通知 ✅
> 14:33:26  库存告警巡检：扫描 2 仓，新增 0 / 刷新 2 / 失败 0          ← 0 失败 ✅
> ```
> 路径：`ap-orchestrator → ap-gateway(AK/SK) → ap-agent 取数 → ap-gateway → ap-agent 写通知`。
> **同时也证明 `/api/terminal/**` 走 AK/SK 通道是通的**（无凭证时的 403 只是"没带凭证"）。

**⚠️ 注意区分两个方向**（这是本条故障最容易被搞混的地方）：

| 方向 | 路径 | 状态 |
|---|---|---|
| **出站** 编排层 → 网关 | `ap-orchestrator → ap-gateway:8090`（AK/SK 签名） | ✅ **已恢复**（14:33 实测 200） |
| **入站** 网关 → 编排层 | `ap-gateway → http://localhost:8125` | ❌ **500（唯一剩余故障）** |

## 四、🔍 发现的既有问题（**均与容器化无关**，逐条已用 A/B 或证据确认）

| # | 问题 | 确认方法 | 影响 |
|---|---|---|---|
| 1 | **`admin` 账号登录不了** | 备份 dump 里 `api_db.a_user.admin` 的 hash 就是 `acfb46fe…`（≠ `SHA2('123456')`）；种子脚本写的是 123456 且**无任何脚本改过它** → 运行期被改过 | **管理台登不进去**。重置：`UPDATE api_db.a_user SET password_hash=SHA2('新密码',256) WHERE user_code='admin'` |
| 2 | `/digitalHuman/**`、`/oa/**` 无 nginx 反代 → 静态回退成 portal.html | 对比原生 `/etc/nginx/sites-available/portal`，**同样只有 `/admin/`、`/`、`/api/` 三个 location** | 那两个前缀的接口无法经 80 端口访问（原生也如此） |
| 3 | 缺必填参数返回 `code:50000 系统错误` 而非参数错误码 | `GlobalExceptionHandler` 把 `MissingServletRequestParameterException` 归到 `SYSTEM_ERROR` | 报错信息误导（应给 40000x） |
| 4 | **RabbitMQ 反序列化一直失败** | 原生 `/var/log/aismp/aismp-backend.log` **命中 38,658 次**，容器 35 分钟仅 6 次 | Spring AMQP 4.0 默认白名单不含 `java.util.*`；**缓存失效通知链路不通**。修法见完成报告 §3.6 |
| 5 | `api_db.a_user` 与 `terminal_db.a_user` **同名不同数据**（12 行 vs 7 行，admin 密码还不一样） | 直接查两库 | 排查登录问题时极易查错表（我第一轮就查错了） |

## 五、结论

**容器间通信与业务链路是通的** —— 门户 7 个数据接口 + 管理端 3 个接口 + 调拨工单 + 登录登出，
全部取到**真实业务数据**（`totalStock=28354`、库龄分析、智能体/工具列表、token 用量），
证明 `nginx → 网关 → [lb://agent / lb://backend / lb://digital-human] → MySQL/PG` 整条链路可用，
**Nacos 服务注册与发现也实测有效**。

**当前唯一的功能性故障是编排层 3 个接口 500**，根因在网关 yml 的硬编码路由（见 §三），一行改动 + 重新编译即可。
