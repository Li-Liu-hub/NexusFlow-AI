## 一、为什么必须重新部署，而不只是改代码

改的不只是字符串，有三处**落在运行时数据/配置里**，代码改完不部署等于没改：

| 项 | 旧值 | 新值 | 不改的后果 |
|---|---|---|---|
| Nacos 服务注册名 | `zmbwl-agent` 等 | `aismp-agent` 等 | 网关 `lb://aismp-agent` 找不到实例 → 全站 503 |
| 网关 AK | `zmbwl-console` | `aismp-console` | 网关签名校验失败 → 服务方调用全 403 |
| 平台账号口令盐 | `zmbwl-platform` | `aismp-platform` | `MD5(SALT+123456)` 变化 → `user` 表账号登录失败 |
| 数字员工工具 `serviceName` | `zmbwl-agent` | `aismp-agent` | `ApiCallToolCallback` 按服务名做 Nacos 服务发现 → 工具调用全失败 |

## 三、踩到的坑（都可复现，别再踩）

1. **`collect-artifacts.sh` 在改 groupId 后会失败**
   `mvn -f aismp-backend/pom.xml package` 报
   `Could not find artifact com.aismp:aismp-common:jar:0.0.1`。
   根聚合工程里虽然声明了 `<modules>`，但脚本是**逐模块**构建，不走 reactor。
   → 先 `mvn clean install`（装 common / client-sdk 进本地仓库）再跑脚本。

2. **`collect-artifacts.sh` 的 ESBUILD_BINARY_PATH 指错了版本**
   原来指向 `D:\env\esbuild\esbuild.exe`（0.28.2），而管理台依赖的 esbuild 是 0.21.5 →
   `Cannot start service: Host version "0.21.5" does not match binary version "0.28.2"`。
   → 改指 `D:\env\esbuild\esbuild-admin.exe`（0.21.5）。已在脚本里加注释与版本提醒。

3. **`--base=/admin/` 被 Git Bash 路径转换破坏（会白屏！）**
   Git Bash 把 `/admin/` 当成 Unix 路径，转成
   `/WorkBuddy/resources/vendor/PortableGit/admin/`，产物 index.html 里写进这个前缀，
   管理台必然白屏。现象是 vite 警告 `"base" option should start with a slash`。
   → `MSYS_NO_PATHCONV=1`；并在脚本末尾**加了产物自检**（index.html 必须含
   `src="/admin/assets/`，否则直接 exit 1，防止白屏产物静默上线）。

4. **`docker compose up -d` 改 TAG 后没有重建容器**
   本次实测：`.env` 已改 `TAG=20261013-aismp`，`docker compose config` 也正确解析出新镜像，
   但 `up -d` 之后 5 个应用容器仍是旧镜像（`Up 23 hours`）。
   → 用 `up -d --force-recreate --no-deps <服务列表>` 才切过去（`--no-deps` 避免重启中间件）。

5. **上传助手要小心 MSYS 路径转换两个方向**
   - 不加 `MSYS_NO_PATHCONV=1`：远端路径 `/tmp/x` 会被转成 `C:/tmp/x`；
   - 加了之后**本地脚本路径** `/d/env/ssh_upload.py` 不再转换，Python 会去找 `d:\d\env\...`。
   → 远端路径用 `/tmp/x`，本地脚本路径写 `D:/env/ssh_upload.py`，两者混用同一行。
