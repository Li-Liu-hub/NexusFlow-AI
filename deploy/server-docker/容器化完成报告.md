## 3. 过程中修掉的 6 个真问题（都靠读日志/源码/实测定位）

| # | 问题 | 根因与修法 |
|---|---|---|
| 1 | **构建脚本 `rm -rf` 被拦** | 本机 `NODE_OPTIONS` safe-delete 守卫拦 `mktemp` 目录的 rm，返回 127 让 `set -e` 杀掉整个脚本 → 改成 `\|\| true` |
| 2 | **`warn: command not found`** | 脚本里漏定义 `warn` 函数，推送失败时反而自己死掉 → 补上 |
| 3 | **推送瞬时失败** | 国内经 Docker Desktop 代理推 ~800MB，收尾阶段会掉线 → 加 4 次重试 + **不再吞错误输出** + 每镜像构建完立即推送 |
| 4 | **postgres 反复重启** | **postgres 18 改了 PGDATA 约定**：18+ 必须挂 `/var/lib/postgresql`，挂 `/var/lib/postgresql/data` 会被 entrypoint 判为"无用挂载"退出 |
| 5 | **nacos 退出码 255** | ① 镜像 entrypoint **无条件要求 `NACOS_AUTH_TOKEN`**（即使关鉴权）② 镜像默认 `JVM_XMN=512m` **比我们设的 Xmx=192m 还大**，参数自相矛盾 |
| 6 | **nacos 一直 unhealthy** | healthcheck 路径 `/nacos/actuator/health` 是 `deployment.type=merged` 才有的端点；standalone server 模式实测应改用 `/nacos/v1/ns/operator/metrics`（返回 `{"status":"UP"}`） |

## 3.5 ⚠️ 容器化引发的一处真实故障（已修复，但必须记录）

### 现象
门户静态页 200，但**任何 `/api/**` 请求全部 403** —— 看起来像"容器间通信全废"。

### 根因（不是网络，是网关应用层的一个白名单）
`aismp-gateway/.../CustomGlobalFilter.java` 有一道**来源地址白名单**：

```java
// 修复前：Arrays.asList("127.0.0.1")  ← 精确匹配
// 修复后：Arrays.asList("127.", "172.28.")  ← 前缀匹配
private static final List<String> IP_WHITE_PREFIXES = Arrays.asList("127.", "172.28.");
```

`ServerHttpRequest#getLocalAddress()` 返回的是**连接的本端地址**：
- 原生部署：网关跑在宿主机 → 本端地址 = `127.0.0.1` → 精确匹配通过
- **容器化后：网关监听在容器 IP → 本端地址 = `172.28.0.11` → `"172.28.0.11".equals("127.0.0.1")` 失配 → 403**

网关日志可证：`请求来源地址：172.28.0.11`（网关自己的容器 IP），`请求来源地址：/172.28.0.7:54794`（ap-nginx 容器）。

**结论：服务间网络从来没坏**（Nacos 注册 IP+端口全对、容器间 HTTP 全通、业务接口能取到真实数据），
坏的只是网关这一道**应用层的地址白名单**。

### 修复验证
| 路径 | 修复前 | 修复后 |
|---|---|---|
| `/api/auth/login` | 403 | **405**（已放行，走到路由） |
| `/api/admin/agent/list` | 403 | **401「缺少 Bearer token」**（已放行，正确要求令牌） |
| `/api/terminal/**` 无 Bearer | 403 | 403（**这个是正常的**：双通道路径走 AK/SK 签名，缺签名当然拒） |

端到端：`POST /api/auth/login {userCode:svc_orchestrator, password:svc-orch-2026}` → 200 拿到 token →
带 Bearer 调 `/api/terminal/stat/cards` → `{"totalStock":28354,"longAging":12759}` **真实业务数据**。

### ⭐ 排查方法论教训（我在这里判断错过一次）
我最初做了 A/B：临时启原生网关打同一请求，也得到 403 → 据此判定"设计行为、非回归"。**这个 A/B 无效** ——
当时我只启了原生网关、**没启原生后端**，于是 `invokeUser == null` → 403（源码里**另一种** 403 原因）。
**我把两个不同原因的 403 混为一谈了。**

> **正确做法**：直接读源码把 `FORBIDDEN` 的**所有出口**列出来（该过滤器里有 3 处），再逐条比对现象；
> 而不是靠"两边都报 403"推断等价。**A/B 控制不住变量时，结论不能下。**

## 3.6 🐞 顺带发现的长期 bug（★ 与容器化无关，原生就存在）

backend 每约 25 秒报一次：
```
ListenerExecutionFailedException: Failed to convert message
Caused by: SecurityException: Attempt to deserialize unauthorized class java.util.HashMap
           (spring-amqp-4.0.4 → SerializationUtils.checkAllowedList)
```

**实测证明非容器化引入**：原生 `/var/log/aismp/aismp-backend.log`（末行 13:53:03，即停服那一刻）
命中 **38,658 次**；容器内跑 35 分钟只 6 次。

根因：**Spring AMQP 4.0 给 Java 反序列化加了默认白名单，而 `java.util.*` 不在其中**，
消息恰好是 Java 序列化的 Map → 监听器一直失败（缓存失效通知链路因此不通）。
这是 Spring Boot 3→4 / Spring AMQP 3→4 迁移的遗留问题。

**✅ 已修复（2026-10-10 14:53 上线并验收通过）**

采用「最小改动」——新增 `aismp-backend/src/main/java/com/aismp/project/config/RabbitMqConfig.java`：

```java
@Bean
public SimpleMessageConverter simpleMessageConverter() {
    SimpleMessageConverter converter = new SimpleMessageConverter();
    converter.setAllowedListPatterns(List.of("java.util.*", "java.lang.*", "com.aismp.*"));
    return converter;
}
```
**刻意保持 Java 序列化协议不变**（只放开消费端校验，生产端网关不动）。
Spring Boot 会把唯一的 `MessageConverter` Bean 同时应用到 `RabbitTemplate` 与监听容器工厂。

**为什么网关侧不用改**：网关的 `CacheInvalidationConsumer` 收的是 `@Payload String`，
String 在 `SimpleMessageConverter` 里走 `text/plain` 分支，**不触发 Java 反序列化检查**。
→ 所以本修复**只动后端一个类，不碰网关**。

**验收结果**

| 项 | 修复前 | 修复后 |
|---|---|---|
| `Attempt to deserialize unauthorized` | 累计 48 次（原生 38,658 次） | **新增 0 次** |
| `invoke.count.queue` 积压 | 48 条，且持续增长 | **0 条** |
| `异步计数成功` 日志 | **0 次**（从未成功过） | **67 次** |
| 业务链路 | — | portal 200 / admin 200 / `stat/cards` → `totalStock=28354` |

**一个反直觉的细节**：异常发生在 `@Payload` **参数解析阶段** →
消费方法体**根本没进入** → `InvokeCountConsumer` 里写的 `channel.basicNack(tag,false,false)`
**根本不会执行**。所以消息不会被丢弃，而是被 Spring AMQP 按自己的默认策略 **requeue 回队列**，
形成**毒消息死循环**（反复消费、反复失败、日志无限增长）。
这解释了原生日志为什么能累计 38,658 次 —— 不是 38,658 条消息，而是少数消息被反复重试。
修复后这 48 条积压消息被**正确消费并落库**（不是丢弃）。

**长期建议**：改用 `Jackson2JsonMessageConverter`（可读、跨语言、无 Java 反序列化安全面），
**但生产端与消费端必须同时切换**，只换一端会更糟。

### 日常更新流程（改完代码后怎么做）★ 最常用

**先记住：现在其实是三段，不是两段**

```
① git push          → 进 Gitee（备份/协作用）        ← 对部署没有直接作用
② 本机构建+推送镜像 → 进 Docker Hub jsyl6/ap-*       ← ★ 只有这一步决定部署内容
③ 服务器 pull + up  → 容器换成新镜像
```
① 不触发任何构建（要自动，得把 `.workflow/push.yml` 的 Gitee Go 流水线扩成构建镜像）。

**三类改动，处理方式完全不同**

| 你改了什么 | 要做什么 | 停不停服 |
|---|---|---|
| **Java / Python 代码** | ① 本机跑 `build-and-push.sh` ② 服务器跑 `80-update-apps.sh` | 只重启被更新的服务（约 20~30s） |
| **前端**（portal / admin 产物） | 覆盖服务器 `/opt/agent-platform/web/{portal,admin}/` | **不用重启**（bind mount，nginx 直接读文件） |
| **配置**（`docker-compose.yml`、`compose/.env`） | 服务器 `docker compose up -d` | **`restart` 不生效，必须 `up -d`** |

```bash
# ① 本机：自动生成唯一 tag（日期-时分秒-gitsha），末尾会打印 TAG，记下来
cd agent-platform/deploy/server-docker
REGISTRY=jsyl6 bash build-and-push.sh

# ② 服务器：拉取 + 滚动重建 + 自动探活
sudo env REGISTRY=jsyl6 TAG=<上一步打印的tag> bash 80-update-apps.sh
sudo env REGISTRY=jsyl6 TAG=<tag> bash 80-update-apps.sh gateway   # 只更新单个服务
```

> ⚠️ **最容易踩的坑：tag 必须每次不同。**
> `docker compose pull` 默认策略是 **`missing`** —— 本地已有同名 tag 就跳过、**不比对远端 digest**。
> 沿用旧 tag 覆盖推送后，pull 会报 `up to date`，容器**继续跑旧镜像**，极难发现。
> `80-update-apps.sh` 内部用 `pull --policy always` 绕开了；你手动敲 `docker compose pull` 时要记得。
> `build-and-push.sh` 的默认 tag 已改成「日期-时分秒-gitsha」，天然唯一。

> ⚠️ **另一个坑（我踩了）**：`TAG` 是 **5 个应用共用**的，改它会让**所有引用它的服务都被判定为"配置变化"而重建**，
> 哪怕 4 个镜像内容完全没变（compose 比对的是 image 引用字符串）。
> 我原本预告"只重建 backend"，实际 4 个服务一起重启了约 46 秒。
> **想只重启一个服务**：不改 `TAG`，直接对目标服务 `up -d --force-recreate <服务名>`；
> 要么给 compose 加**按服务覆盖 tag**（如 `image: ${REGISTRY}/ap-backend:${BACKEND_TAG:-$TAG}`）。

**回滚**：`80-update-apps.sh` 每次会把当前镜像清单存到 `compose/.images-before-*.txt`，
从里面拿到旧 tag 后按同样命令重跑即可。

**镜像仓库不可达时的替代路径（2026-10-10 实测走过一次）**：
服务器上就装了 Docker，**可以完全绕开镜像仓库**——
① 把新 jar + `Dockerfile.jdk21` 传到 `/opt/agent-platform/build/{jars/,}`；
② `docker build -f Dockerfile.jdk21 --build-arg JAR=aismp-backend.jar -t jsyl6/ap-backend:<新tag> .`（实测 **<25 秒**）；
③ 未变的镜像用 `docker tag` 打本地别名到同一 tag（**瞬时，零网络**）；
④ 改 `compose/.env` 的 `TAG` 后 `up -d`。
**触发场景**：本机推 Hub 时 DNS 解析到 IPv6（`[2a03:2880:...]`）且 IPv6 不通 → `connectex: A connection attempt failed`。

## 7. ⭐ 容器化必须修的「硬编码 127.0.0.1 / localhost」清单（系统性风险）

**这是本次容器化真正的坑所在。** 代码/配置里散落着硬编码的本机回环地址 —— 原生部署时它们恰好成立，
容器化后**每一个都是一条断掉的链路**。排查方法：`grep -rnE "127\.0\.0\.1:(端口)|localhost:(端口)"`。

| # | 位置 | 值 | 能否用环境变量覆盖 | 容器内后果 | 状态 |
|---|---|---|---|---|---|
| 1 | `CustomGlobalFilter.IP_WHITE_PREFIXES`（Java 常量） | `["127.0.0.1"]` **精确匹配** | ❌ 不能用 env | **所有 `/api/**` 403** | ✅ 已修（改前缀 `["127.","172.28."]`） |
| 2 | gateway `application.yml` route `orchestrator_route` | `uri: http://localhost:8125` | ❌ **硬编码** | 网关→编排层 **500**（`/orchestrator/**`） | ❌ **未修** |
| 3 | gateway `application.yml` route `orchestrator_portal_route` | `uri: http://localhost:8125` | ❌ **硬编码** | **500**（`/api/orchestrator/**`） | ❌ **未修** |
| 4 | gateway route `api_route`（兜底 `/api/**`） | `uri: http://localhost:8123` | ❌ 硬编码 | 未登记路径返回 500 而非 404 | ⚠️ 影响小 |
| 5 | backend `aismp.digital-human.base-url` | `${DIGITAL_HUMAN_BASE_URL:http://127.0.0.1:8126}` | ✅ **有占位符** | 管理端代理数字员工失败 | ✅ 已在本 compose 补 `DIGITAL_HUMAN_BASE_URL=http://digital-human:8126` |
| 6 | orchestrator `llm.py:15` `_CHARGE_URL` | `http://127.0.0.1:7529/...` | ❌ **模块级常量，无占位符** | 编排层 token 计费上报失败 | ❌ 需改代码（编排层） |
| 7 | orchestrator `config.py:34` `DIGITAL_HUMAN_DIRECT_URL` | `http://127.0.0.1:8126` | ✅ pydantic Settings 可覆盖 | 仅当 `DIGITAL_HUMAN_VIA_GATEWAY=False` 才用 | ⚠️ 默认不触发 |
| 8 | 各应用 `spring.cloud.nacos.discovery.ip: 127.0.0.1` | 写死 | ❌ 不能用 yml 删，但可用 `SPRING_CLOUD_NACOS_DISCOVERY_IP` 覆盖 | 注册成 127.0.0.1 → 网关 `lb://` 永远找不到 | ✅ 已用固定 IP `172.28.0.11~15` |

### 第 2/3 条的确切修法（★ 500 的真正修复点）

**关键认知：`/api/orchestrator/**` 的 500 是网关产生的，不是编排层产生的。**
证据：500 的响应体是 Spring 格式错误 JSON，且**编排层容器日志里根本没有这条请求**。

所以**改编排层本身不解决这个问题** —— 必须改**网关**的 `application.yml`：

```yaml
# 改前
- id: orchestrator_route
  uri: http://localhost:8125        # ← 容器里 localhost = 网关自己的回环
  predicates: [Path=/orchestrator/**]
- id: orchestrator_portal_route
  uri: http://localhost:8125        # ← 同上
  predicates: [Path=/api/orchestrator/**]

# 改后（加占位符，容器/原生都能用同一份代码）
- id: orchestrator_route
  uri: ${ORCHESTRATOR_BASE_URL:http://127.0.0.1:8125}
  predicates: [Path=/orchestrator/**]
- id: orchestrator_portal_route
  uri: ${ORCHESTRATOR_BASE_URL:http://127.0.0.1:8125}
  predicates: [Path=/api/orchestrator/**]
# api_route 同理：uri: ${MOCK_BASE_URL:http://127.0.0.1:8123}
```
再在 compose 的 gateway 服务加 `ORCHESTRATOR_BASE_URL: http://orchestrator:8125`（和 `MOCK_BASE_URL`）。
**改完必须重新编译网关并出新 tag 镜像**（yml 打进 jar 里，光改 compose 没用）。

> ⚠️ 注意 §5 里那条 tag 规则：**出镜像必须用新 tag**，否则服务器 `pull` 默认策略 `missing` 会跳过，白忙一场。

### 验证服务注册是否真的可用（不只是"注册成功"）

注册日志只能证明"注册动作成功"，**不能证明发现链路可用**。更强的证据是**网关按 `lb://` 找到实例并取回真实数据**：

| 路由 | uri | 验证结果 |
|---|---|---|
| `terminal_biz_route` | `lb://aismp-agent` | ✅ `/api/terminal/stat/cards` → `{"totalStock":28354}` 真实数据 |
| `portal_backend_auth_route` | `lb://aismp-backend` | ✅ `/api/auth/login` → 405（走到路由了） |
| `digital_human_portal_route` | `lb://aismp-digital-human` | ✅ `/api/admin/agent/list` → 401（digital-human 自己要求令牌） |

**三条 `lb://` 路由全部实测可用** → Nacos 注册 + 发现是好的。

## 8. 数据卷的可见性（为什么在 1Panel 里看不到"卷"）

数据**没有丢**，用的是 **bind mount** 挂到 `/opt/agent-platform/data/`，
而 1Panel 的「存储卷」页面只列 `docker volume`（命名卷）→ **bind mount 天生不显示**。

实测数据（合计 1.2G）：`mysql 261M`（含 `api_db`/`terminal_db`/`nacos_config` 等 7 库）、
`nacos 875M`、`pg 65M`（`orch_conversation=71` 行、`vector_store=48` 行、`orch_message`、`spring_ai_chat_memory`）、
`rabbitmq 280K`（`mnesia`）、`redis 32K`。

### 想让它在 1Panel 里"看得见"（可选，我可以改）

改用**命名卷 + bind driver**，物理位置不变、备份方式不变，但会出现在 Docker/1Panel 的卷列表里：

```yaml
volumes:
  mysql-data:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /opt/agent-platform/data/mysql
```
生效需要 `docker compose up -d --force-recreate` 相关服务（**数据不动，只是换个挂载方式**）。
代价：换挂载方式期间对应服务短暂不可用。
