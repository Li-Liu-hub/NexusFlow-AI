## 2. 推荐路径（阶段 1）：只容器化 5 个应用

### 为什么是「只应用」+「host 网络」

- **应用 jar 里的地址全是写死的 `127.0.0.1`**（`credentials.env` 只提供密码，不给地址）。
  用 `network_mode: host` 之后，容器的 `127.0.0.1` 就是宿主的 `127.0.0.1`，
  于是 **5 个应用一行配置都不用改**就连上原生 MySQL/PG/Redis/RabbitMQ/Nacos。
  换 bridge 网络就得把地址改成 `host.docker.internal` 并逐个覆盖配置项 —— 自找的复杂度。
- **中间件只有 ~160MB 且已调优**，容器化收益低、迁移风险高，先不动。
- nginx 保持原生（它才 6.7MB，而且门户入口现在工作正常，不动它最稳）。

### 完整命令序列

```bash
# ============ ① 在服务器上：构建并推送镜像 ============
# 前提：把本目录传到服务器（假设 /opt/agent-platform-secure/server-docker/）
cd /opt/agent-platform-secure/server-docker

sudo -E REGISTRY=ccr.ccs.tencentyun.com/<你的命名空间> \
     TAG=$(date +%Y%m%d) \
     JARS_DIR=/opt/app \
     LOGIN=1 \
     bash build-and-push.sh

# 编排层镜像需要构建上下文；服务器上 /opt/app/orchestrator 是源码目录，直接当上下文
# （build-and-push.sh 会在编排层上下文缺失时提示，按提示补即可）

# ============ ② 在服务器上：拉镜像并切换 ============
sudo -E REGISTRY=ccr.ccs.tencentyun.com/<你的命名空间> TAG=$(date +%Y%m%d) \
     bash deploy-from-registry.sh --install-docker

# ============ ③ 回滚（单元文件没被动过）============
sudo -E REGISTRY=... TAG=... bash deploy-from-registry.sh --rollback
```

`deploy-from-registry.sh` 会自动：装 Docker → 写 compose 变量文件 → `docker login` → `pull`
→ 停并 disable 5 个 systemd 单元 → `compose up -d` → 逐个端口探活 → 打印内存。

### 换机器/重装后只需要

```bash
docker compose --env-file /opt/agent-platform-secure/compose.env -f docker-compose.apps.yml up -d
```
（凭据仍在 `/opt/agent-platform-secure/credentials.env`，没有进 git）

## 3. 内存账：引入 Docker 到底划不划算

上一轮我们讨论过「Docker 在 Linux 上只会增加内存」。**在那里结论没变：dockerd+containerd 常驻约 +150MB，是纯新增，不替换任何东西。**
但结合这次实测，账要重新算：

| 项 | 变化 |
|---|---:|
| 2026-10-10 调优释放（5 个应用 + 编排层） | **−814 MB** |
| 2026-10-10 调优释放（Nacos，对比它自己的冷启动态 800MB） | **−215 MB** |
| 引入 Docker（dockerd + containerd + shim） | **+150~220 MB** |
| 净结果 | **仍有约 −800 MB 余量** |

**也就是说：现在装 Docker 是"付得起"了 —— 这不是我改口，是前提变了。** 之前 `available` 只有 845MB 且已在换页，
加 150MB 是把安全垫吃掉；现在 `available` 1379MB，加完还剩 ~1.2GB。

而且 Docker 在这里带来两件原生方案给不了的东西：

1. **`mem_limit` 是硬上限**（超了内核 OOM-kill 该容器，而不是拖垮整机）。
   在 3.7G 的机器上，这正是防止「某个服务内存失控导致 sshd 都 fork 不动」的护栏 ——
   这台机器 10/7 就发生过一次（`mem-optimize.sh` 的注释里记着：门户响应 16.9s、sshd banner 超时）。
2. **换机器/重装只要 pull**，不用再重建 JDK、重写 systemd 单元。

`docker-compose.apps.yml` 里的 `mem_limit` 按「实测 RSS × 约 1.5」给（gateway 384m / backend 448m /
kernel 416m / agent 512m / 编排层 256m，合计上限 2016m），不是贴着实测值给 —— 免得稳定后被误杀。

## 5. 对现有 `docker-compose.yml`（阶段 2 用）的偏差修正

现有那份如果要用于「全量容器化」，有 5 处和真机不符，**别直接拿来跑**：

### 5.1 JDK 版本错了（最严重）
```yaml
backend:  build: { dockerfile: Dockerfile.jdk8 }   # ← 错
gateway:  build: { dockerfile: Dockerfile.jdk8 }   # ← 错
```
实测：`aismp-backend/pom.xml` 与 `aismp-backend/aismp-gateway/pom.xml` 都是 `<java.version>21</java.version>`；
真机上 4 个应用跑的全是 `java-21-openjdk-amd64`。**只有 `aismp-interface` 是 8，而它不部署。**
→ 4 个应用统一用 `Dockerfile.jdk21`。

### 5.2 Nacos 版本错了
```yaml
nacos:  image: nacos/nacos-server:v2.2.3-slim   # ← 真机是 3.2.4
```
真机 `/opt/nacos-3.2.4`，且 `-Dnacos.deployment.type=merged`（console+server 同进程）。
→ 镜像换 `nacos/nacos-server:v3.2.4`，环境变量名也对不上（现有 compose 用 `NACOS_AUTH_TOKEN`，
真机是 `NACOS_TOKEN_SECRET` + `NACOS_IDENTITY_*`）。

> ⚠️ 顺带一个实测数据：**Nacos 3 冷启动态是 800MB（原参数）/ 585MB（本次调参后）**，
> 而不是我们最初扫到的 268MB（那是跑了 2.5 天后的沉淀态）。全量容器化时给它 448m 的 `mem_limit` **会把它 OOM-kill**，
> 至少要 768m。

### 5.3 应用层要改成从仓库拉
```yaml
backend:  build: { ... }        # ← 改成 image: ${REGISTRY}/ap-backend:${TAG}
```

### 5.4 `.env.example` 的键名要和 `credentials.env` 对齐
现有模板里 `RABBIT_USER=api_user`、`NACOS_AUTH_TOKEN=...`，而真机 `credentials.env` 是
`RABBIT_USER=aismp`、`NACOS_TOKEN_SECRET=...`。不对齐会导致中间件容器起来但应用连不上。

### 5.5 中间件容器化必须先迁数据
要迁的东西：`terminal_db` + `api_db`（MySQL）、`terminal_kb` + pgvector 扩展（PG）、
RabbitMQ 用户/队列、Nacos 配置与注册数据。现有 `migrate/export-from-server.sh` +
`migrate/import-to-docker.sh` 是为此写的，但**没有在"容器与原生并存"的场景验证过**。
→ 建议演示之后再动，且务必先 `mysqldump` / `pg_dump` 全量备份。

## 6. 更长期的方案（阶段 3，可选）

把 `.workflow/push.yml`（Gitee Go，已在跑 pytest + Java 编译）扩展成：

```
push main → 跑测试 → mvn package → docker build → docker push 到 TCR
```

这样服务器只负责 `pull && up -d`，彻底摆脱「本机 Docker 起不来」和「jar 来源不可追溯」两个问题。
Gitee Go 免费额度对演示项目够用。
